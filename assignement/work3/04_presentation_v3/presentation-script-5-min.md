## ช่วงที่ 1 · ปกและบริบท (0:00 - 0:25, 25 วินาที, 56 คำ)

สวัสดีครับ วันนี้ผมนำเสนอบทความ **Prompt-to-SQL Injections** โดยโรดริโก เปโดร และคณะ จากมหาวิทยาลัยลิสบอน ในงานประชุม **ICSE 2025** ครับ

งานวิจัยนี้ศึกษาความเสี่ยงเมื่อเว็บแอปพลิเคชันใช้โมเดลภาษาแปลงคำถามเป็น SQL ค้นฐานข้อมูล โดยผู้วิจัยได้วิเคราะห์ช่องโหว่ ทดสอบการโจมตี และพัฒนาระบบป้องกันชื่อ **LangShield** ครับ

## ช่วงที่ 2 · ปัญหา: เมื่อ LLM เป็นผู้เขียน SQL แทนโปรแกรมเมอร์ (0:25 - 1:05, 40 วินาที, 117 คำ)

ผู้วิจัยทดสอบบนเว็บหางานจำลองด้วย FastAPI และ PostgreSQL ผ่านเฟรมเวิร์กยอดนิยมอย่าง LangChain และ LlamaIndex ครับ

ผู้วิจัยพบว่าการป้องกันเดิมสี่ข้อด้านซ้ายล้มเหลว: ข้อแรก **Parameterized query** ใช้ไม่ได้ เพราะโมเดลสร้างโครง SQL ใหม่ทั้งประโยค จึงไม่มีพารามิเตอร์ให้แยกตรวจ ข้อสอง **ข้อห้ามในพรอมต์** ถูกหลบเลี่ยงได้ง่าย เพียงอ้างเป็นผู้ใช้อื่น โมเดลก็คืนข้อมูลส่วนตัวออกมา ข้อสาม **ภัยแบบอ้อม** ที่แอบฝังคำสั่งลวงไว้ในข้อมูลประกาศงาน จนโมเดลตอบว่าไม่มีงาน และข้อสี่ **บัญชีฐานข้อมูลมีสิทธิ์เต็ม** เมื่อสั่งละเลยคำสั่งเดิม โมเดลจึงสร้างคำสั่งลบตารางจริง **DROP TABLE users CASCADE** ตามตัวอย่างฝั่งขวาครับ

## ช่วงที่ 3 · สถาปัตยกรรม LangChain 3 ขั้น และการโจมตี 7 รูปแบบ (1:05 - 1:55, 50 วินาที, 147 คำ)

ภาพซ้ายแสดงสถาปัตยกรรมสามขั้น โดยมี **LLM** ทำหน้าที่เขียน SQL, **LangChain** เป็นมิดเดิลแวร์ตัวกลาง, และ **DBMS** เป็นฐานข้อมูลรันคำสั่ง: ขั้นแรก ส่งคำถามให้ LLM แปลงเป็น SQL ขั้นสอง นำ SQL ไปรันบน DBMS และขั้นสาม ส่งผลลัพธ์กลับให้ LLM เรียบเรียงคำตอบ จุดนี้ทำให้ข้อมูลภายนอกไหลกลับเข้าสู่โมเดลได้ครับ

ตารางขวาแสดงผลเจ็ดรูปแบบบน GPT-3.5 ซ้ำยี่สิบครั้ง ค่าหนึ่งคือสำเร็จทุกครั้งครับ กลุ่ม **U** ไม่มีข้อห้าม จึงสั่งลบ แก้ไข หรือดึงข้อมูลได้ทั้งหมด กลุ่ม **RD** มีข้อห้าม แต่ผู้โจมตีพิมพ์หลบเลี่ยงสำเร็จทุกกรณี ส่วนกลุ่ม **RI** เป็นภัยทางอ้อม โดย **RI.1** บน SQL Agent สำเร็จร้อยละหกสิบ เพราะการคิดหลายขั้นช่วยจับความขัดแย้งได้บ้าง แต่กรณี **RI.2** ที่สั่งแก้ไขข้อมูลและค้นหาใหม่ Agent ถูกหลอกสำเร็จเต็มร้อยละร้อยครับ

## ช่วงที่ 4 · LangShield: ป้องกัน 3 จุด ด้วย 4 เทคนิค (1:55 - 2:45, 50 วินาที, 124 คำ)

ผู้วิจัยจึงพัฒนา **LangShield** วางจุดดักสามตำแหน่งครับ: จุด **a** ดึงข้อมูลผู้ใช้ใส่พรอมต์ล่วงหน้า หากพอ โมเดลจะตอบได้โดยไม่ต้องค้นฐานข้อมูล

จุด **b** ตรวจ SQL ก่อนส่งไป DBMS สองชั้น: หนึ่ง **Query checking** อนุญาตเฉพาะ SELECT ใช้เวลาศูนย์จุดเจ็ดมิลลิวินาที จึงตัดคำสั่ง DROP ทิ้งได้ทันที และสอง **Query rewriting** ปรับ SQL ให้จำกัดตามผู้ใช้ ใช้เวลาหนึ่งจุดแปดเจ็ดมิลลิวินาที เช่น แปลงเป็นคิวรีซ้อนล็อกเฉพาะผู้ใช้หมายเลขห้า ส่วนจุด **c** ใช้ **LLM guard** ตรวจผลลัพธ์จากฐานข้อมูลว่ามีคำสั่งแฝงหรือไม่ โดยมี **DeBERTa-v3** คัดกรองเบื้องต้น สี่เทคนิคนี้ผสานกันหยุดการโจมตีทั้งเจ็ดรูปแบบได้สมบูรณ์ครับ

## ช่วงที่ 5 · ผลการทดลอง: โจมตีได้เกือบทุกกรณี และป้องกันได้เมื่อซ้อนหลายชั้น (2:45 - 3:45, 60 วินาที, 171 คำ)

ด้านแอปจริง กรอบขวาบน ผู้วิจัยนำแอปห้าตัวบน GitHub รันใน Docker ให้ Red Team เจาะระบบ ผลคือโจมตีสำเร็จถึง **ยี่สิบสองจากยี่สิบสามกรณี** ยืนยันว่าระบบจริงแทบไม่มีการป้องกันครับ

กราฟซ้าย ผู้วิจัยประเมิน **LLM guard** ใน Hook c ดักคำสั่งแฝงหกสิบรายการ: หากตรวจเฉพาะผลลัพธ์ GPT-3.5 แท่งสีเทาจับได้เพียงร้อยละห้าสิบห้า แต่เมื่อส่งคำถามร่วมด้วยและสั่งให้เขียนวิเคราะห์เหตุผล หรือ Thought อัตราตรวจจับพุ่งเป็น **ร้อยละหนึ่งร้อยเต็ม ชนะ Rebuff ซึ่งเป็นเกณฑ์มาตรฐานโอเพนซอร์สที่ทำได้ร้อยละเจ็ดสิบแปด** เพราะ Rebuff ขาดบริบทเฉพาะของ SQL และไม่พบผลบวกลวงในข้อมูลปกติหนึ่งร้อยห้าสิบรายการ

กรอบล่าง เพื่อลดความหน่วง ผู้วิจัยใช้ **DeBERTa** คัดกรองด่านแรก ช่วยลดเวลารวมลงร้อยละห้าสิบหก จากหนึ่งร้อยสี่สิบเจ็ด เหลือหกสิบสี่วินาที จึงได้ทั้งความปลอดภัยสูงสุดและความเร็วพร้อมใช้งานจริงครับ

## ช่วงที่ 6 · จุดแข็ง จุดอ่อน และข้อจำกัด (3:45 - 4:25, 40 วินาที, 102 คำ)

ในการวิเคราะห์ งานนี้มี **จุดแข็ง** สามประการครับ: หนึ่ง จัดหมวดหมู่ภัยเจ็ดแบบเป็นระบบจนใช้เป็นเกณฑ์ทดสอบได้ สอง มีหลักฐานครอบคลุม ทั้งโมเดลเจ็ดตัว แอปจริง และแจ้งเตือนผู้พัฒนาอย่างรับผิดชอบ และสาม ป้องกันหลายชั้นโดยนำกฎแน่นอนมาช่วยลดภาระ AI

ส่วน **ข้อจำกัด** ได้แก่: ชุดข้อมูลทดสอบยังมีขนาดเล็กและไม่ได้รายงานค่าเบี่ยงเบนมาตรฐาน ยังไม่ประเมินผู้โจมตีที่ปรับตัวหลบ guard โดยเฉพาะ และผลยังผูกกับ LangChain รุ่นศูนย์จุดหนึ่งจุดศูนย์ โดยยังไม่ได้ใช้ Row-Level Security ของฐานข้อมูลครับ

## ช่วงที่ 7 · บทสรุปและการประยุกต์ใช้งาน (4:25 - 4:55, 30 วินาที, 83 คำ)

โดยสรุป ผู้วิจัยชี้ว่า **Parameterized query เพียงอย่างเดียวไม่เพียงพออีกต่อไป** เมื่อโมเดลภาษาเป็นผู้สร้าง SQL ความปลอดภัยต้องควบคุมผ่านสถาปัตยกรรมระบบ

โดยผู้วิจัยเสนอแนวทางสามข้อครับ: หนึ่ง สร้างตัวกลางตรวจและปรับแต่ง SQL ก่อนส่งไปฐานข้อมูล สอง เปิดใช้นโยบาย **Row-Level Security** ในระดับฐานข้อมูลควบคู่กัน และสาม ใช้โมเดลคัดกรองข้อมูลก่อนส่งกลับคืนให้ AI การป้องกันที่แท้จริง ต้องคุมทั้งคำสั่งที่ส่งไปและข้อมูลที่ดึงกลับมาครับ ขอบคุณครับ
