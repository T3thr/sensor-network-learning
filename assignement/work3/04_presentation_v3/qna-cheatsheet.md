## กลุ่ม A: ความเหมาะสมของบทความ

### Q1. บทความนี้เกี่ยวกับเครือข่ายเซนเซอร์อย่างไร
**แนวตอบ:** คำสั่งงานให้เลือกหัวข้อที่เกี่ยวกับโครงงานจบได้ ผมเลือกด้าน API security ที่ทำอยู่จริง แต่เชื่อมกับวิชานี้ได้ตรง: แดชบอร์ด IoT ที่ให้ถามว่า "ห้องไหนอุณหภูมิสูงสุด" ใช้สถาปัตยกรรม Text-to-SQL แบบเดียวกัน และข้อมูลที่อุปกรณ์หรือผู้ใช้ส่งเข้าฐานข้อมูลก็เป็นช่องทางโจมตีแบบอ้อม (RI.1) ได้

### Q2. ทำไมเลือกบทความนี้แทนงาน AIOps หรือ Kafka ที่ใกล้งานเรามากกว่า
**แนวตอบ:** ค้นแล้วไม่มีบทความ Kafka ที่เป็น Open Access ในปี 2024-2026 (ผลค้น `Kafka OR "event streaming"` มี Open Access 1 รายการและไม่ตรงหัวข้อ) ส่วนงาน AIOps ที่คัดไว้เป็นตัวสำรองไม่มี Baseline เชิงตัวเลข งานนี้ได้คะแนนคัดเลือก 33/35 สูงสุด ปัญหาเล่าจบใน 1 ประโยค และมีตัวเลขเทียบ Baseline ชัด

### Q3. ICSE เป็นงาน IEEE จริงหรือ และเป็น Conference ไม่ใช่ Journal ใช่ไหม
**แนวตอบ:** ใช่ครับ ชื่อเต็มคือ 2025 IEEE/ACM 47th International Conference on Software Engineering อยู่ใน IEEE Xplore ประเภท Conferences, IEEE Doc ID 11029790, DOI 10.1109/ICSE55347.2025.00007 และเป็น Open Access ดาวน์โหลดได้โดยไม่ต้องล็อกอิน

## กลุ่ม B: ความเข้าใจเชิงเทคนิค

### Q4. P2SQL ต่างจาก SQL Injection แบบเดิมอย่างไร ทำไม parameterized query ใช้ไม่ได้
**แนวตอบ:** SQL Injection เดิมคือผู้ใช้แทรกข้อความลงใน "ช่องว่าง" ของ SQL ที่โปรแกรมเมอร์เขียนไว้ parameterized query จึงแก้ได้ด้วยการแยกโครงคำสั่งกับค่าอินพุต แต่ใน P2SQL ผู้ใช้ไม่ได้แทรก SQL ตรง ๆ ผู้ใช้หลอก LLM ให้เขียน SQL ทั้งประโยคขึ้นใหม่ จึงไม่มีโครงคำสั่งเดิมให้ป้องกัน (Section VI-A, p. 1776)

### Q5. การโจมตีแบบตรง (RD) กับแบบอ้อม (RI) ต่างกันอย่างไร อันไหนอันตรายกว่า
**แนวตอบ:** RD ผู้โจมตีพิมพ์เข้าแชตบอตเอง RI ผู้โจมตีฝากพรอมต์ไว้ในแถวข้อมูล เช่น ช่องคำอธิบายงาน แล้วรอให้ผู้ใช้คนอื่นถาม (p. 1772-1773) RI อันตรายกว่าเพราะเหยื่อเป็นคนกระตุ้นเอง และตัวกรองที่ดูแค่ข้อความของผู้ใช้จะมองไม่เห็น นี่คือเหตุผลที่ต้องมี Hook c ที่ตรวจผลลัพธ์จากฐานข้อมูล

### Q6. SQL chain กับ SQL agent ต่างกันอย่างไร
**แนวตอบ:** Chain รัน SQL ได้ 1 คำสั่งต่อคำถาม Agent รันหลายคำสั่งต่อเนื่องได้ (Section II, p. 1770) Agent จึงเปิดทางให้ RI.2 คือ UPDATE อีเมลเหยื่อแล้ว SELECT ปิดร่องรอย ซึ่ง chain ทำไม่ได้ (Table II แสดงว่า RI.2 มีผลเฉพาะ agent)

### Q7. SQL query rewriting ทำงานอย่างไร ต่างจากใส่ WHERE ในพรอมต์ตรงไหน
**แนวตอบ:** Parser แทนตารางอ่อนไหวด้วยคิวรีซ้อน เช่น `SELECT email FROM users` เป็น `SELECT email FROM (SELECT * FROM users WHERE user_id = 5) AS users_alias` (p. 1776) ต่างกันตรงที่เงื่อนไขนี้ถูกบังคับด้วยโค้ด LLM จะเขียนอะไรมาก็ไม่มีผล ส่วนการเขียนข้อห้ามในพรอมต์ถูกหลบได้ด้วย "I am now user 2" (Finding 2)

### Q8. LLM guard ทั้ง 3 รุ่นต่างกันอย่างไร ทำไมรุ่นที่ 3 ดีที่สุด
**แนวตอบ:** รุ่น 1 เห็นแค่ผลลัพธ์ SQL, รุ่น 2 เห็นคำถามด้วย, รุ่น 3 เห็นคำถามและต้องเขียน "ความคิด" 1 ประโยคก่อนตอบ True/False บน GPT-3.5 ได้ 55%, 88%, 100% ตามลำดับ (Figure 3, p. 1778) เพราะการเห็นคำถามทำให้รู้ว่าผลลัพธ์ส่วนไหนไม่เกี่ยวกับคำถาม แต่ต้องบอกด้วยว่าบน GPT-4 รุ่น 3 ได้ 93% ต่ำกว่ารุ่น 1 ที่ได้ 98%

## กลุ่ม C: การทดลองและตัวเลข

### Q9. ตัวเลข 100% น่าเชื่อถือแค่ไหน
**แนวตอบ:** เชื่อได้ในขอบเขตแคบครับ มาจาก prompt ร้ายของ red team 60 รายการบน GPT-3.5 และ false positive 0 จาก 150 รายการที่ GPT-4 สร้างขึ้น (p. 1778) ผู้วิจัยยอมรับเองว่าผลนี้ "valid only for our limited experimental setup" ตัวเลขที่ใหญ่กว่าคือ 99.55% บน 1,120 prompts แต่ชุดนี้ขยายด้วย LLM จากชุดเดิม จึงยังไม่ใช่ผู้โจมตีที่ปรับตัวได้ ไม่มีการรายงาน SD หรือช่วงความเชื่อมั่น

### Q10. Baseline คืออะไร เทียบกันยุติธรรมไหม
**แนวตอบ:** Baseline คือ Rebuff เครื่องมือตรวจ Prompt Injection แบบ open source ได้ 78% บน GPT-3.5 และ 80% บน GPT-4 ผู้วิจัยอธิบายว่า Rebuff ไม่ได้ออกแบบมาเฉพาะ SQL และฐานข้อมูลเวกเตอร์ของมันจับได้ยากเมื่อพรอมต์ร้ายปนอยู่กับแถวอื่น (p. 1778) มองว่าเทียบได้ในแง่เครื่องมือสำเร็จรูป แต่ Rebuff ไม่ได้ถูกปรับให้เข้ากับงานนี้ ความต่างจึงส่วนหนึ่งมาจากการออกแบบเฉพาะทาง

### Q11. 22 จาก 23 นับมาจากไหน
**แนวตอบ:** จาก Table VI (p. 1775) มีแอป 5 ตัว × โมเดล 2 รุ่น × การโจมตี RD.1, RI.1, RI.2 ตัดกรณีที่ไม่เกี่ยวข้อง (N/A) ออกเหลือ 23 กรณี red team สำเร็จ 22 กรณี ล้มเหลว 1 กรณีคือ RI.2 บน streamlit_agent-sql_db กับ GPT-3.5 ส่วนเครื่องมืออัตโนมัติสำเร็จ 11 กรณี (Finding 8)

### Q12. Overhead ของระบบป้องกันรับได้ไหมสำหรับ API จริง
**แนวตอบ:** แยกเป็น 2 ส่วน SQL checking 0.7 ms และ rewriting 1.87 ms ต่อคิวรี รับได้แม้ใน API ทั่วไป ส่วน LLM guard ใช้ประมาณ 0.43 วินาทีต่อตัวอย่างหลังใช้ DeBERTa (จาก 147.30 เหลือ 64.15 วินาทีต่อ 60 prompts, Figure 4) ผู้วิจัยบอกเองว่ารับได้ในแชตบอตแต่อาจมากไปสำหรับงานที่ต้องการความหน่วงต่ำ (p. 1778) ถ้าเป็นระบบของผม จะเรียก LLM guard เฉพาะแถวที่มาจากข้อมูลที่ผู้ใช้กรอกเอง

## กลุ่ม D: วิพากษ์และต่อยอด

### Q13. ถ้าให้เลือกข้อจำกัดที่ร้ายแรงที่สุดข้อเดียว คือข้อไหน
**แนวตอบ:** การไม่ทดสอบผู้โจมตีที่รู้ว่ามี LLM guard (Adaptive Attacker) เพราะ LLM guard เองก็เป็น LLM ที่ถูก Prompt Injection ได้ ผู้วิจัยยอมรับใน Section VI-A ว่า "potential circumvention through targeted attacks" แต่ไม่ได้วัด ตัวเลข 100% จึงบอกได้แค่ว่ากัน prompt ชุดที่มีอยู่ได้ ไม่ได้บอกว่ากันผู้โจมตีที่ตั้งใจหลบได้

### Q14. ทำไมไม่ใช้สิทธิ์ของฐานข้อมูล (Database Roles หรือ Row-Level Security) ไปเลย
**แนวตอบ:** ผู้วิจัยพิจารณาแล้วแต่ตัดออกเพราะต้องทำที่ระดับ DBMS ไม่ใช่ระดับเฟรมเวิร์ก (p. 1776) ผมเห็นว่านี่คือจุดอ่อนเชิงออกแบบ ในระบบจริงควรใช้ทั้งคู่: บัญชีฐานข้อมูลของแชตบอตอ่านได้อย่างเดียวและเปิด Row-Level Security ของ PostgreSQL เป็นชั้นสุดท้ายที่รับประกันผล ส่วน rewriting ใน LangShield เป็นชั้นเสริม ซึ่งผู้วิจัยเองก็แนะนำให้ "combine application-level and database-level protections" ใน Section VIII

### Q15. จะนำไปใช้ในโครงงานจบอย่างไร ด้วยเทคโนโลยีที่ถนัด
**แนวตอบ:** บทที่ 1-2 ใช้การจำแนก 7 รูปแบบและผล red team เป็นที่มาและกรอบทฤษฎี บทที่ 3 ออกแบบ API ที่มี LLM ตรงกลางแบบ Hook: เขียน Gin middleware ใน Go ที่ตรวจว่า SQL เป็น `SELECT` แล้วเติม `user_id` จาก claim `sub` ของ JWT ที่ Keycloak ออกให้ ไม่เชื่อค่าจากข้อความ และให้ PostgreSQL บังคับ Row-Level Security ซ้ำ ส่วนการวัดผลจะใช้ 7 รูปแบบในบทความเป็นชุดทดสอบ และเพิ่ม adaptive attack ที่บทความยังไม่ได้ทำ
