2

LangShield: ป้องกัน 3 จุด ด้วย 4 เทคนิค

ภาพที่ 2: Hook a, b, c บนเส้นทางการทำงานของ LangChain (Pedro et al., 2025, Fig. 2, p. 1777)

Query rewriting ใน Hook b: ตัวแยกวิเคราะห์ SQL แทนที่ตารางอ่อนไหว

ก่อน: SQL ที่ LLM เขียน
SELECT email FROM users
หลัง: เมื่อผู้ใช้ที่ล็อกอินคือ user_id = 5
SELECT email FROM ( SELECT * FROM users WHERE user_id = 5 ) AS users_alias

หน้าที่ของแต่ละจุดดัก

a

ก่อนสร้างพรอมต์

In-prompt data preloading: ใส่ข้อมูลของผู้ใช้ปัจจุบันไว้ล่วงหน้า LLM จึงไม่ต้องสร้าง SQL แลกกับโทเคนที่เพิ่มขึ้น

b

หลัง LLM เขียน SQL

Query checking: อนุญาตเฉพาะ SELECT (0.7 ms)
Query rewriting: ผูกเงื่อนไขของผู้ใช้ (1.87 ms)

c

หลังได้ผลจากฐานข้อมูล

LLM guard: LLM อีกตัวตัดสิน True หรือ False โดยมี DeBERTa-v3 คัดกรองก่อนเพื่อลดการเรียก LLM

ไม่มีเทคนิคใดกันได้ครบทั้ง 7 แบบ แต่เมื่อใช้ทั้ง 4 เทคนิคร่วมกัน การโจมตีทุกแบบที่พบถูกหยุดได้ (Table VII, Finding 12)

จุดแข็ง จุดอ่อน และข้อจำกัด

จุดแข็ง

1

นิยามภัยใหม่อย่างเป็นระบบ

การโจมตี 7 รูปแบบบนสามมิติ (มีข้อห้ามหรือไม่, ตรงหรืออ้อม, อ่านหรือเขียน) ใช้เป็นรายการทดสอบระบบได้ทันที

2

หลักฐานหลายชั้น

2 เฟรมเวิร์ก 7 LLM และแอปจริง 5 ตัว ยืนยันโดย Red Team ภายนอก พร้อมแจ้งช่องโหว่แก่ผู้พัฒนา

3

ป้องกันแบบ Defense in Depth

กฎที่ให้ผลแน่นอนและเร็ว (0.7 ms, 1.87 ms) อยู่ด้านหน้า ส่วน LLM guard ใช้เฉพาะภัยแบบอ้อม

จุดอ่อนและข้อจำกัด

1

ชุดประเมินการป้องกันเล็ก

ตัวเลข 100% มาจากพรอมต์ 60 รายการ และข้อมูลปกติ 150 รายการที่ GPT-4 สร้างขึ้นเอง ไม่มีค่า SD

2

ไม่ทดสอบ Adaptive Attacker

ผู้โจมตีที่รู้ว่ามี LLM guard อาจเขียนพรอมต์ที่หลอกทั้ง LLM หลักและผู้ตรวจพร้อมกัน

3

ขอบเขตผูกกับรุ่นซอฟต์แวร์

LangChain 0.1.0 และ GPT รุ่นปี 2023 และไม่ใช้ Row-Level Security ของฐานข้อมูล

บทสรุปและการประยุกต์ใช้งาน

บทสรุปสำคัญ (Key Takeaways)

1

สิทธิ์ต้องบังคับที่ระดับระบบ

ข้อห้ามในพรอมต์ไม่ใช่การควบคุมสิทธิ์ที่แท้จริง ต้องตรวจทาน SQL และผูกเงื่อนไขผู้ใช้ด้วยโค้ดหรือระบบฐานข้อมูล

2

การป้องกันเชิงลึกหลายชั้น

ไม่มีเทคนิคเดี่ยวใดกันได้ครบ 7 แบบ ต้องผสาน In-prompt preloading, Query checking, Query rewriting และ LLM guard

3

ต้นทุนและข้อจำกัดของ LLM Guard

แม้ตรวจจับได้ 100% บนชุดทดสอบ แต่เพิ่ม Latency ในการตอบสนอง และยังต้องประเมินรับมือกับ Adaptive Attacker ในอนาคต

แนวทางการประยุกต์ใช้งาน (Practical Applications)

1

Secure Text-to-SQL Gateway

ประยุกต์ใช้ Query checking และ AST rewriting เป็น API Gateway หน้าฐานข้อมูล อนุญาตเฉพาะ SELECT และกำกับสโคปข้อมูลองค์กร

2

การผสาน Database Row-Level Security (RLS)

เปิดใช้นโยบาย RLS ใน PostgreSQL เพื่อให้ระบบจัดการฐานข้อมูลเป็นปราการด่านสุดท้าย ป้องกันข้อมูลรั่วไหลแม้โมเดลสร้าง SQL พลาด

3

Agentic Security & Guardrail Pipeline

นำแนวคิด DeBERTa early exit และ Auxiliary LLM guard มาสร้างไปป์ไลน์ตรวจสอบข้อมูลขาออกสำหรับระบบ AI Agent ในงานวิศวกรรม
