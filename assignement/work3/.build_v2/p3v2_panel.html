2. ปัญหา Single Point of Failure

Federated Learning ทำงานอย่างไร (Section 2)

  1. aggregator สร้างโมเดลตั้งต้น
  2. worker ฝึกด้วยข้อมูลของตัวเอง ข้อมูลดิบไม่ออกจากเครื่อง
  3. worker ส่งเฉพาะพารามิเตอร์ที่เปลี่ยน
  4. aggregator รวมพารามิเตอร์ เช่น หาค่าเฉลี่ย
  5. ทำซ้ำหลายรอบ

จุดอ่อน (Section 2.1)

การรวมโมเดลยังอยู่ที่ aggregator เครื่องเดียว ถ้าฮาร์ดแวร์เสีย เครือข่ายขาด หรือเหตุไม่คาดคิด การฝึกหยุดทั้งระบบ และความคืบหน้าที่ยังไม่บันทึกหายไป

ในเครือข่ายเซนเซอร์ เกตเวย์ที่รวมข้อมูลก็มีจุดอ่อนแบบเดียวกัน

ทางเลือกเดิม (Section 3)ข้อดีเหตุผลที่ผู้เขียนไม่เลือก
Gossip / swarm learningไม่มีจุดกลางยังใหม่และซับซ้อนเกินกว่าจะใช้ซ้ำได้ทั่วไป
Distributed Ledger Technologyโปร่งใส กันการแก้ไขข้อมูลกินพลังประมวลผล พื้นที่ และพลังงานของอุปกรณ์ IoT
Behera et al. (Raft)เลือก aggregator ใหม่อัตโนมัติไม่สำเนาสถานะ และเป็นเอกสาร 5 หน้าที่ยังไม่ผ่าน peer review

3. Raft ใน 3 กลไก

บทความสรุป Raft ใน Section 4.1 และให้อ่านรายละเอียดจากบทความต้นฉบับของ Ongaro และ Ousterhout (2014) ส่วนนี้อธิบายเท่าที่ต้องใช้ในการนำเสนอ

1. Leader Election

follower ที่ไม่ได้รับ heartbeat จนหมด randomised election timeout จะเป็น candidate เพิ่มเลข term และขอคะแนนเสียง ผู้ได้เสียงข้างมากของสมาชิกทั้งหมดเป็น leader

2. Heartbeat

leader ส่งสัญญาณเป็นระยะ ถ้าเงียบนานเกิน timeout จะเกิดการเลือกตั้งรอบใหม่ การสุ่ม timeout ลดโอกาสที่คะแนนเสียงแตก

3. Log Replication

leader ส่ง log entry ให้ follower และถือว่า commit เมื่อเสียงข้างมากตอบรับ ในบทความ log คือ checkpoint ของพารามิเตอร์

เครื่องคำนวณ Quorum

สูตร Q = floor(N/2) + 1 และ f_max = floor((N-1)/2) มาจากนิยามของ Raft ไม่ได้อยู่ในบทความ ใช้เพื่อวิพากษ์จุด 1 worker ใน Fig. 3

4. สถาปัตยกรรมและ Self-Recovery

ระดับ (Table 1)สิ่งที่สำเนาผลเมื่อ aggregator ดับ
Level 0ไม่มีความคืบหน้าหาย
Level 1พารามิเตอร์บนดิสก์ของ aggregator เดิมต้องรอเครื่องเดิมกลับมา
Level 2ไม่มี แต่เลือกผู้นำใหม่ด้วย Raftฝึกใหม่จากศูนย์
Level 3 (บทความเลือก)พารามิเตอร์ที่รวมแล้วฝั่ง aggregatorผู้นำใหม่ฝึกต่อจาก checkpoint ล่าสุด
Level 4เพิ่มพารามิเตอร์ของ worker ทุกตัวครบที่สุด แต่ส่งข้อมูลซ้ำซ้อนมาก

Self-Recovery Workflow 4 ขั้น (Section 5.3)

  1. Leader election: ทุกโหนดเริ่มจากการเลือกตั้ง ผู้ชนะเป็น aggregator ทุกโหนดมีโค้ดของทั้งสองบทบาท
  2. Check state: aggregator ตรวจสถานะที่สำเนาไว้ (รอบที่ฝึกแล้ว รอบที่เหลือ พารามิเตอร์ล่าสุด)
  3. Checkpoint 3 จุด: หลังตั้งค่าพารามิเตอร์ หลังรวมผลการฝึก และหลังรวมผลการประเมิน เขียนลง replicated key-value ของ PySyncObj ที่คัดลอกแบบ asynchronous
  4. Aggregator alive?: worker ตรวจหลังทุกรอบ ถ้าไม่ตอบ ทุกโหนดกลับไปเลือกตั้ง แล้ว aggregator ใหม่ฝึกต่อจาก checkpoint

เชิงอรรถใต้ Fig. 2 ระบุว่าภาพตัดข้อความเลือกตั้งหลายรอบ การตอบรับ และ heartbeat ออกเพื่อความชัด

6. ซิมูเลเตอร์ Raft Failover ในเครือข่ายเซนเซอร์

แบบจำลองเพื่อการเรียนรู้ ใช้กฎของ Raft: election timeout สุ่ม 150 ถึง 300 ms, heartbeat ทุก 60 ms, ชนะเมื่อได้เสียงข้างมากของสมาชิกทั้งหมด และ commit checkpoint เมื่อเสียงข้างมากตอบรับ เวลาในแบบจำลองไม่เทียบกับ 1.27 ถึง 3.76 วินาทีในบทความ ซึ่งรวมเวลาของ Python, Flower และ Wi-Fi บน Raspberry Pi

Dataset

CIFAR-10 เป็นภาพ ไม่ใช่ time series จากเซนเซอร์ พารามิเตอร์ 250 kB เล็กกว่าโมเดลจริง ผู้เขียนยอมรับว่าโมเดลระดับ MB จะทำให้ทราฟฟิกหนักขึ้นมาก

ขอบเขตความผิดพลาดและความคงทน

Raft รับมือเฉพาะ crash fault ไม่กัน aggregator ที่โกง และสถานะอยู่ในหน่วยความจำ ถ้าดับพร้อมกันทั้งคลัสเตอร์ ความคืบหน้าหาย

การเชื่อมโยงกับงานจริง (ความเห็นของผู้จัดทำ)

  • เกตเวย์เซนเซอร์: ให้เกตเวย์ 3 หรือ 5 เครื่องเป็นสมาชิก Raft ส่วนโหนดเซนเซอร์ที่ใช้แบตเตอรี่เป็นเพียง FL client ตรงกับ selective state replication ใน Section 7.1
  • etcd และ Kafka KRaft: ใช้ฉันทามติตระกูล Raft เหมือนกัน แต่เขียน log ลงดิสก์และใช้ quorum ขนาดเล็ก แก้จุดอ่อนเรื่องดับพร้อมกันและทราฟฟิก
  • Event-driven backend ด้วย Go: scheduler หรือ ordered consumer ใช้รูปแบบเลือกผู้นำ + checkpoint offset แบบเดียวกัน
