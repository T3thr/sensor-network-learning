## 4. สาระของบทความหลักจากฉบับเต็ม (สำหรับใช้ในขั้นเขียนรายงาน)

### 4.1 ปัญหา
Distributed ledger ที่มีอยู่ขยายความสามารถตามจำนวน validator ไม่ได้ ระบบที่ขยายได้ก็ต้องเสียความปลอดภัยหรือความเป็นกระจายศูนย์ (Section I และ Table IV) ผู้แต่งตั้งเป้าให้ throughput โตแบบเชิงเส้นตามจำนวน validator โดยยังเป็น permissionless

### 4.2 ความท้าทาย 3 ข้อและ Threat Model
1. เลือกกลุ่ม validator ที่เป็นตัวแทนทางสถิติ โดยทนต่อ Sybil attack
2. ทำให้โอกาสที่ shard ใดถูกยึดตลอดอายุระบบต่ำมาก ด้วยการสร้าง shard ใหม่เป็นระยะให้ใหญ่พอและสุ่มแบบมีอคติไม่ได้
3. จัดการธุรกรรมที่เกี่ยวกับหลาย shard ให้ถูกต้องแบบ atomic

Threat model: validator ไม่ซื่อสัตย์ไม่เกิน 25% (n = 4f), ผู้โจมตีปรับตัวได้ช้าในระดับ epoch (mildly adaptive), สมมติว่าช่องทางสื่อสารระหว่าง validator ที่ซื่อสัตย์เป็นแบบ synchronous

### 4.3 การออกแบบ
1. **Sharding:** ทุก epoch ใช้ VRF เลือกผู้นำ แล้วให้ผู้นำรัน RandHound สร้างค่าสุ่มเพื่อจัด validator เข้า shard ทยอยสลับ validator ครั้งละ k = log(n/m) เพื่อให้ shard ยังทำงานระหว่างเปลี่ยน epoch
2. **ByzCoinX:** BFT consensus ภายใน shard ใช้โครงสร้างการสื่อสารแบบกลุ่มที่ความลึกคงที่ ทนต่อโหนดล้มเหลวได้ดีกว่า ByzCoin และ commit บล็อกแบบขนานเมื่อธุรกรรมไม่ขัดแย้งกัน
3. **Atomix:** ธุรกรรมข้าม shard ใช้ 3 ขั้น (Initialize, Lock, Unlock) input shard แต่ละตัวล็อก UTXO แล้วออก proof-of-acceptance หรือ proof-of-rejection จากนั้น client (หรือฝ่ายอื่นเมื่อ time-out) นำ proof ไป commit หรือ abort เพื่อคืนเงินที่ล็อกไว้
4. **State blocks:** สรุปสถานะของ shard เป็นระยะ ให้ validator ใหม่ดาวน์โหลดเฉพาะ state block ล่าสุดแทนการ replay ทั้งสาย
5. **Trust-but-verify:** กลุ่ม optimistic validator ขนาดเล็กยืนยันเร็วสำหรับธุรกรรมมูลค่าต่ำ แล้ว core validator ตรวจซ้ำภายหลัง

### 4.4 คณิตศาสตร์ที่ใช้ (Section VI และ Appendix C)
- Eq. (1): โอกาสที่ shard ขนาด n มีผู้โจมตีไม่เกิน ⌊n/3⌋ คำนวณด้วย binomial distribution เมื่อผู้โจมตีมีสัดส่วน m = 0.25 (สมมติว่ามี validator จำนวนไม่จำกัด)
- Eq. (2): ความล้มเหลวต่อ epoch ≤ Σ (k = 0 ถึง l) (1/4ᵏ) · n · P[X_S] เมื่อ l เข้าใกล้อนันต์จะได้ ≤ (4/3) · n · P[X_S]
- ตัวอย่างที่ผู้แต่งคำนวณ: ผู้โจมตี 12.5% กับ 16 shard ได้ 4 × 10⁻⁵ ต่อ epoch หรือ 1 ครั้งใน 68.5 ปี (ผู้ประเมินตรวจแล้ว: 1 / (4 × 10⁻⁵) = 25,000 วัน ≈ 68.5 ปี)
- โอกาสที่ผู้โจมตีคุมผู้นำติดกัน n ครั้ง ≤ 1/4ⁿ ซึ่งต่ำกว่า 10⁻⁶ เมื่อ n = 10
- Hypergeometric: กลุ่ม 25 จาก 600 โหนด มีโอกาส 99.93% ที่ผู้โจมตีในกลุ่มน้อยกว่า 15
- Eq. (3): ความน่าจะเป็นที่ธุรกรรมใช้ UTXO อยู่ใน shard จำนวน k จาก m shard

### 4.5 การทดลองและผล (Section VIII)
- DeterLab 60 เครื่อง (Intel E5-2420 v2, RAM 24 GB) จำกัดแบนด์วิดท์ 20 Mbps หน่วง 100 ms ข้อมูลตั้งต้นคือ 10,000 บล็อกแรกของ Bitcoin
- 1,800 โหนด 25 shard ผู้โจมตี 12.5%: 13,000 tps ผู้แต่งเทียบว่าประมาณ 3 เท่าของค่าเฉลี่ย Visa (ประมาณ 4,000 tx/s)
- Table II (shard ละ 70 โหนด, ผู้โจมตี 12.5%): 439, 869, 1,674, 3,240, 5,850 tps ที่ 1, 2, 4, 8, 16 shard
- Table I: ยืนยันชั้นแรก 1.38 s ในสามค่าแรก และ 4.48 s ที่ shard 600 โหนด ผู้โจมตี 25%; ยืนยันชั้นที่สอง 1.38 s ที่ [4, 1%] และ 55.89 s, 41.84 s, 62.96 s ที่ [25, 5%], [70, 12.5%], [600, 25%] ตามลำดับ
- Epoch transition: RandHound ใช้เวลามากกว่า 70% ของการ bootstrap กรณีแย่สุดประมาณ 3 ชั่วโมง ซึ่งผู้แต่งถือว่ารับได้เมื่อ epoch ยาว 1 วัน
- ByzCoinX: throughput เพิ่ม 20% และ latency ต่อบล็อกลด 35% เมื่อแบ่งบล็อกใหญ่หนึ่งบล็อกเป็นสี่บล็อกย่อยที่ทำงานพร้อมกัน แต่เมื่อเพิ่มการขนานต่อ ประสิทธิภาพลดลงเล็กน้อย
- State blocks: คุ้มกว่าเมื่อ validator ตามไม่ทันเกิน 19 วัน (2,736 บล็อก Bitcoin)

### 4.6 ข้อจำกัดที่ผู้แต่งยอมรับเอง (Section X)
1. ต้นทุน bootstrap ของ epoch อยู่ในระดับนาทีและมากพอที่จะต้องใช้ epoch ยาวระดับวัน
2. throughput ขึ้นกับรูปแบบธุรกรรม ถ้าทุกธุรกรรมแตะทุก shard ใช้ shard เดียวจะดีกว่า
3. การป้องกัน censorship ยังพึ่งการที่ validator ซื่อสัตย์ตรวจพบแล้วเปลี่ยนผู้นำ
4. ไม่ได้วิเคราะห์แรงจูงใจทางเศรษฐศาสตร์ของผู้เข้าร่วม ใช้เพียงการแบ่งซื่อสัตย์กับไม่ซื่อสัตย์
5. ไม่เหมาะกับผู้โจมตีที่ปรับตัวเร็ว
6. Security analysis เป็นแบบ informal (ผู้แต่งเขียนไว้ต้น Section VI)

## 5. ประเด็นวิจารณ์ที่ผู้ประเมินตรวจพบเพิ่ม

1. **ผลทดลอง scale-out ไม่ได้แยกผลของธุรกรรมข้าม shard** Table II เพิ่มเกือบเชิงเส้น (1,674 / 439 ≈ 3.8 เท่าที่ 4 shard) แต่ Appendix C ของผู้แต่งเองประเมินว่าธุรกรรมจริงส่วนใหญ่ข้าม shard และความเร็วจาก 1 ไป 4 shard จะเหลือราว 1.56 เท่า บทความไม่ได้รายงานการทดลองที่มีสัดส่วนธุรกรรมข้าม shard ตามจริง เป้าหมาย "Scale-out แบบเชิงเส้น" ใน Section III จึงยังไม่ได้พิสูจน์ในภาระงานจริง
2. **Eq. (1) พิมพ์ผิด** (PDF หน้า 591) ขอบบนของผลรวมเขียนเป็น n ถ้าอ่านตรงตัว ผลรวมจะเท่ากับ 1 เสมอตามทฤษฎีบททวินาม ขอบบนที่ถูกต้องควรเป็น ⌊n/3⌋
3. **ตัวเลขใน Appendix C ไม่สอดคล้องกันภายใน** (PDF หน้า 597 ตรวจด้วยการคำนวณซ้ำ)
   - สัมประสิทธิ์ (m − k)/m ในสูตรเวียนเกิดทำให้ผลรวมความน่าจะเป็นไม่เท่ากับ 1 ค่าที่ถูกคือ (m − k + 1)/m
   - โอกาสที่ธุรกรรม 3 UTXO อยู่ใน shard เดียว (3 shard) ควรเป็น 1/9 ≈ 11.1% ไม่ใช่ 3.7% (= 1/27)
   - ค่า 1.56 เท่าตรงกับกรณี 4 UTXO ถ้าใช้ 3 UTXO ตามที่ข้อความระบุจะได้ประมาณ 1.875 เท่า
   - ข้อสังเกตเพิ่มของผู้ประเมิน (ขึ้นกับสมมติฐาน): สูตร speed-up ของผู้แต่งคือ m · Σ P(k)/k ซึ่งเป็นการเฉลี่ยค่า 1/k ถ้าสมมติว่าแต่ละ shard ที่ธุรกรรมแตะต้องใช้งานตรวจหนึ่งหน่วย และความจุรวมของระบบคือ m หน่วย ปริมาณงานที่ได้จะเป็น m / E[k] ซึ่งได้ประมาณ 1.46 เท่า (4 UTXO) หรือ 1.73 เท่า (3 UTXO) ต่ำกว่าสูตรของผู้แต่งเสมอตามอสมการของ Jensen (E[1/k] ≥ 1/E[k]) และยังไม่นับงานเพิ่มของ Atomix ในขั้น Lock กับ Unlock ตัวเลข 1.56 จึงน่าจะเป็นค่าที่มองในแง่ดี
   - ข้อสรุปเชิงคุณภาพยังถูก คือความเร็วจริงต่ำกว่า Table II มาก
4. **กรณีผู้โจมตี 25% ที่ระดับ throughput ของ Visa ไม่ได้วัดจริง** ผู้แต่งประมาณว่าต้องใช้ประมาณ 4,200 โหนดใน 7 shard เพื่อให้ได้ 4,000 tps แต่แพลตฟอร์มทดลองรับภาระนั้นไม่ได้ ตัวเลขนี้จึงเป็นค่าประมาณ ทั้งที่ threat model หลักของบทความคือ 25% (การตั้งค่า [600, 25%] ที่ 1,800 โหนดมีผลวัดใน Fig. 6 และ Table I แต่ throughput ต่ำกว่า 4,000 tps)
5. **เครือข่ายเป็นการจำลอง** ใช้ DeterLab จำกัดแบนด์วิดท์และหน่วงคงที่ทุกลิงก์ ไม่มีความแปรปรวนของ WAN จริง ต่างจาก Red Belly (SP 2021) ที่ทดลองบน VM กระจายหลายทวีป
6. **Table IV เปรียบเทียบข้ามเงื่อนไข** ตัวเลขของระบบอื่นมาจากคนละบทความและคนละสภาพการทดลอง
7. **Fig. 5 อ้างอิงสลับด้าน** ข้อความใน Section VI-B เรียกด้านซ้ายและขวาของรูปกลับกับคำบรรยายใต้รูป
8. **ข้อแลกเปลี่ยนของ trust-but-verify** การยืนยันชั้นแรกยอมรับโอกาสน้อยกว่า 10% ที่จะเสี่ยงต่อ double-spending ผู้แต่งจำกัดให้ใช้กับธุรกรรมมูลค่าต่ำ นอกจากนี้ข้อความใน Section VIII-B ระบุว่าการยืนยันขั้นสุดท้ายของธุรกรรมความเสี่ยงสูงยังไม่ถึงหนึ่งนาที แต่ Table I ในกรณีผู้โจมตี 25% แสดง 62.96 s
9. **ข้อมูลตั้งต้น** ใช้ 10,000 บล็อกแรกของ Bitcoin บทความไม่ได้อธิบายว่าสร้างภาระงานระดับ 13,000 tps จากชุดข้อมูลนี้อย่างไร เป็นคำถามที่ควรตรวจต่อในขั้นเขียนรายงาน
10. **ตัวเลข throughput ที่ 1,800 โหนดไม่ตรงกันสามแหล่ง** (ตรวจเพิ่มในขั้นเขียนรายงาน) ที่ผู้โจมตี 12.5% บทนำ (หน้า 584) ระบุ 6,000 tps, Section VIII-B (หน้า 593) ระบุ 13,000 tps ใน 25 shard ส่วนแท่งกราฟ [70, 12.5%] ใน Fig. 6 (หน้า 592) อ่านจากพิกัดเวกเตอร์ใน PDF ได้ราว 6,800 tps (regular) และ 19,900 tps (trust-but-verify) โดยตรวจการสอบเทียบแกนแล้ว เส้น Visa อ่านได้ราว 4,120 tps ใกล้ค่า 4,000 ที่ระบุ นอกจากนี้ Table IV (หน้า 595) ระบุ scale-out ของ OmniLedger เป็น 2,400 validator ทั้งที่การทดลองที่รายงานมีสูงสุด 1,800 โหนด รายงานและสไลด์จึงอ้าง Table II และค่าที่อ่านจาก Fig. 6 พร้อมระบุว่าเป็นค่าประมาณ

## 6. ความเชื่อมโยงกับทักษะของนิสิต

ตารางนี้เป็นการเทียบของผู้ประเมินเพื่อช่วยให้นิสิตอธิบายด้วยประสบการณ์ตัวเอง ไม่ได้อยู่ในบทความ และต้องพูดถึงความต่างด้วยทุกครั้ง

| แนวคิดในบทความ | สิ่งที่นิสิตใช้ในงานจริง | จุดที่ต่างกัน |
|---|---|---|
| Shard และการกระจาย UTXO ตาม hash | Kafka partition ที่กระจายข้อความตาม key | Kafka ไม่ได้ออกแบบให้ทนต่อโหนดที่ตั้งใจโกง (Byzantine) ส่วน OmniLedger ต้องสุ่มสมาชิก shard ใหม่ทุก epoch เพื่อกันผู้โจมตี |
| Atomix (Lock แล้ว Unlock to Commit หรือ Unlock to Abort) | Two-phase commit และ Saga pattern ใน microservices | Atomix ให้ client เป็นผู้ขับเคลื่อนและใช้ proof ที่มีลายเซ็นของ shard แทน coordinator กลาง ส่วน Saga ใช้ compensating transaction |
| State blocks สำหรับ ledger pruning | Snapshot, checkpoint และ log compaction | State block ต้องมีลายเซ็นรวมของ shard เพื่อให้ validator ใหม่เชื่อได้โดยไม่ replay |
| ByzCoinX commit บล็อกแบบขนานตาม dependency ของธุรกรรม | Concurrency ด้วย goroutine และการจัดการ conflict ในฐานข้อมูล | ผลทดลองแสดงว่าการขนานมากเกินไปทำให้ประสิทธิภาพลดลง เพราะต้นทุน cryptography ต่อบล็อกคงที่ |
| Prototype ภาษา Go | ภาษาหลักที่นิสิตใช้ที่ Codefin | ไม่ได้ตรวจ repository ของผู้แต่งในรอบนี้ |

## 7. ความเสี่ยงและทางสำรอง

1. **หัวข้อไม่ใช่เครือข่ายเซนเซอร์** ใบสั่งงานระบุให้เลือกหัวข้อที่นิสิตสนใจ และแนะนำให้เป็นด้านที่ทำโครงงานจบ (ไม่ได้บังคับให้ตรงวิชา) ถ้าอาจารย์ต้องการความเชื่อมโยงกับวิชา ให้สลับเป็น BACKUP 2 (Burglars' IoT Paradise) ซึ่งตรงทั้งวิชาและทักษะ หรือ Crowd-GPS-Sec ถ้าอาจารย์กำหนดให้เป็นงานเครือข่ายเซนเซอร์โดยตรง
2. **คำว่า blockchain อาจถูกมองเป็นหัวข้อ cryptocurrency** ควรวางกรอบเป็นงาน distributed systems (Byzantine fault tolerance, sharding, atomic commit) ที่ตีพิมพ์ในงานประชุมหลักของ IEEE
3. **เนื้อหากว้าง** บทความมีองค์ประกอบย่อยห้าส่วน การนำเสนอไม่เกินห้านาทีต้องเลือกเล่าเฉพาะแกนหลัก
4. **ไม่เชื่อมกับโครงงาน DivWy** ตามที่นิสิตกำหนดว่ารอบนี้ไม่ต้องยึดโครงงาน ถ้าจะใช้ในเล่มวิทยานิพนธ์ ใช้ได้เพียงเป็น related work ด้าน scalability ของระบบกระจายตัว
5. **ทางสำรองเพิ่มเติม** ถ้าต้องการงาน Open Access ที่มีฮาร์ดแวร์ปลายทางชัดเจน มี Raft Protocol for Fault Tolerance and Self-Recovery in Federated Learning (SEAMS 2024, IEEE 10556381) ที่ทดลองบน Raspberry Pi 3 จำนวน 11 บอร์ด แต่เป็น proof of concept ขนาดเล็ก (ดู `03_search_log.md`)
6. **การเชื่อม OmniLedger กับเครือข่ายเซนเซอร์เป็นความเห็นของนิสิต ไม่ใช่ข้อค้นพบของบทความ** OmniLedger ไม่ได้กล่าวถึงเซนเซอร์หรือ IoT เลย ถ้ารายงานหรือสไลด์เสนอการประยุกต์กับ gateway ของเครือข่ายเซนเซอร์ ต้องเขียนแยกเป็นหัวข้อความเห็นและการประยุกต์ใช้ และระบุชัดว่าเป็นการต่อยอดของผู้นำเสนอ
