## สไลด์ 1 · Publish-Time Optimizations for Web-Based Visualizations

**เป้าหมาย:** อธิบายชื่อเรื่องให้เป็นปัญหาระบบ และระบุว่าผู้วิจัยย้ายงานอะไรไปทำเมื่อใด

**พื้นฐานก่อนอ่าน:** เริ่มจากเว็บหนึ่งหน้าที่มีชาร์ต ไม่ต้องมีพื้นฐานฐานข้อมูลหรือเครื่องมือ Mosaic มาก่อน

### ลำดับอ่านภาพ

- **ชื่อเรื่องกลางหน้า:** อ่านชื่อเต็มครั้งเดียว คำ Publish-Time เป็นจุดสำคัญ: เวลาที่เตรียมงานก่อนเปิดเว็บ ไม่ใช่เวลาโพสต์ข่าวหรือเวลาโหลดไฟล์
- **ผู้แต่งและสถาบัน:** ระบุ Pechuk และ Heer จาก University of Washington เพื่อให้ที่มาชัดเจน หลังจากนั้นเรียกผู้วิจัย
- **ข้อความแนวคิด:** เชื่อมปัญหาการเปิดเว็บกับสามงาน: เตรียมข้อมูล คำนวณทรัพยากร และวาดภาพเริ่มต้น
- **แถบระเบียนด้านล่าง:** IEEE VIS 2025 กับ DOI ใช้ตามต้นฉบับ ไม่ต้องเสียเวลาพูดอ่านเลขทั้งหมด

### เว็บชาร์ตหนึ่งหน้าต้องทำอะไรบ้าง [พื้นฐาน]

ข้อมูลดิบอาจมีหนึ่งแถวต่อเที่ยวบิน แต่ชาร์ตต้องการจำนวนเที่ยวบินต่อวัน ระบบจึงต้องอ่านข้อมูล สรุปตามวัน แล้วแปลงจำนวนเป็นความสูงของแท่ง งานข้อมูลกับงานวาดภาพเป็นคนละขั้น แม้เห็นผลรวมเป็นชาร์ตเดียวกัน
ถ้าชาร์ตเลือกช่วงวันได้ ต้องมีส่วนรับค่าที่เลือก ส่งคำขอใหม่ และปรับภาพตามผลนั้น การเห็นแท่งบนหน้าจอจึงยังไม่รับรองว่าขั้นตอนโต้ตอบพร้อมแล้ว นี่เป็นพื้นฐานที่จะใช้แยก TTR กับ TTA ในสไลด์ 2

### เหตุใดภาพข้อมูลจึงเหมาะกับการเตรียมล่วงหน้า [บทความ]

ภาพที่เผยแพร่มักมีข้อกำหนดคงที่ รู้คอลัมน์ ชนิดภาพ และชนิดอินพุตก่อนใช้งาน คิวรีจึงมีรูปแบบที่คาดได้ เช่น การเลือกช่วงเวลา ทำให้มีโอกาสเตรียมงานซ้ำไว้ก่อน
โอกาสนี้ไม่ใช่หลักประกันว่าจะเตรียมทุกสถานะได้ ถ้าจำนวนช่วงหรือมิติการเลือกมาก ทรัพยากรอาจโตสูง หรือถ้าข้อมูลเปลี่ยนตลอด ผลที่เตรียมไว้อาจล้าสมัย

### แยก Mosaic ออกจาก Mosaic Publisher [บทความ]

Mosaic เป็นสถาปัตยกรรมที่ใช้จัดการภาพ คิวรี และการเชื่อมอินพุตอยู่ก่อนแล้ว ส่วน Publisher คือเครื่องมือที่ผู้วิจัยพัฒนาสำหรับวิเคราะห์และเตรียมทรัพยากรจากข้อกำหนด
บทความนี้ไม่ได้เสนอฐานข้อมูลใหม่ และไม่ได้ทำให้เบราว์เซอร์เลิกใช้ JavaScript ระบบโต้ตอบยังมีงานรันไทม์ เพียงเริ่มจากทรัพยากรที่เตรียมไว้ได้

### เตรียมวัตถุดิบก่อนเปิดร้าน แต่ยังต้องรับรายการสั่ง [อุปมา]

งานเตรียมข้อมูลเหมือนคัดวัตถุดิบ งานผลรวมเหมือนเตรียมส่วนประกอบที่ใช้บ่อย ภาพเริ่มต้นเหมือนจัดจานตัวอย่างให้เห็นทันที แต่รายการที่เปลี่ยนยังต้องมีครัวและพนักงานรับคำสั่ง
อุปมานี้อธิบายการย้ายเวลา ไม่ได้บอกว่าต้นทุนหายไป และไม่ควรนำไปกล่าวว่าเป็นตัวอย่างที่ผู้วิจัยเขียนไว้

ข้อมูลดิบ + ข้อกำหนด → เตรียมก่อนเผยแพร่ → เก็บทรัพยากรใช้ซ้ำ → เปิดเว็บและเริ่มส่วนโต้ตอบ

### ศัพท์ประจำสไลด์

#### Web-Based Visualization

**คำอ่าน:** เว็บ-เบสต์ วิชวลไลเซชัน

**ความหมาย:** การเปลี่ยนข้อมูลเป็นภาพบนเว็บ เช่น ชาร์ตหรือแผนที่ เพื่อมองเห็นรูปแบบที่อ่านจากตารางดิบได้ยาก

**ที่มาของแนวคิด:** Visualization หมายถึงทำให้ข้อมูลมองเห็นได้ ส่วน Web-Based ระบุว่าเปิดผ่านเบราว์เซอร์ แนวคิดจึงรวมทั้งฐานข้อมูล การวาดภาพ และส่วนรับอินพุต

**เหตุที่เกี่ยวข้อง:** งานนี้สนใจช่วงเปิดภาพข้อมูลและเริ่มโต้ตอบ ไม่ได้พัฒนาอัลกอริทึมวาดชาร์ตชนิดใหม่

**ตัวอย่างใช้งาน:** แดชบอร์ดเที่ยวบินสรุปเวลาล่าช้าตามวัน เมื่อเลือกวัน ชาร์ตที่เชื่อมกันเปลี่ยนตาม เป็นตัวอย่างอธิบายบริบท ไม่ใช่ผลทดลองเพิ่มเติม

**คำเกี่ยวข้อง:** Dashboard / Interactive Visualization · Rendering / SVG / Raster / Canvas · Cross-filtering / Linked Views / Brushing / Confidence Interval / Regression Fit

**อ้างอิงบริบท:** Abstract, §1 · PDF หน้า 1

#### Publish-Time Optimization

**คำอ่าน:** พับลิช-ไทม์ ออปทิไมเซชัน

**ความหมาย:** ย้ายงานที่ทำซ้ำได้ไปคำนวณก่อนเผยแพร่ แล้วนำผลลัพธ์ไปใช้เมื่อเปิดเว็บ

**ที่มาของแนวคิด:** Publish คือช่วงจัดเตรียมและเผยแพร่ทรัพยากร Optimization คือปรับวิธีทำงานให้ใช้เวลาและทรัพยากรเหมาะขึ้น งานยังเกิดขึ้นจริงแต่เกิดก่อนเซสชัน

**เหตุที่เกี่ยวข้อง:** เป็นแนวคิดหลักที่รวมการเตรียมข้อมูล แคชผลคิวรี และภาพเริ่มต้น

**ตัวอย่างใช้งาน:** แดชบอร์ดข้อมูลประจำวันคำนวณผลรวมก่อนเปิดบริการหลายเซสชัน หากข้อมูลเปลี่ยนต้องจัดรอบสร้างใหม่

**คำเกี่ยวข้อง:** Run-Time / Runtime · Data Preparation / Column Projection / Transformation · Pre-computation / Pre-aggregation · Pre-rendering / Initial Pre-rendering

**อ้างอิงบริบท:** §1, §3 · PDF หน้า 1–3

#### Run-Time / Runtime

**คำอ่าน:** รัน-ไทม์

**ความหมาย:** ช่วงที่ระบบทำงานเมื่อมีเซสชันใช้งาน รวมการโหลดข้อมูล รันคิวรี วาดภาพ และรับการโต้ตอบ

**ที่มาของแนวคิด:** Run คือทำงาน Time คือช่วงเวลา ต่างจากช่วงเตรียมเผยแพร่ตรงที่ผู้ใช้งานกำลังรอผลอยู่

**เหตุที่เกี่ยวข้อง:** Baseline none คำนวณทุกอย่างตอนรันไทม์ การปรับปรุงไม่ได้ตัดรันไทม์ทิ้ง เพราะภาพโต้ตอบยังต้องเริ่มคอมโพเนนต์

**ตัวอย่างใช้งาน:** การกดตัวกรองที่ไม่เคยเตรียมผลไว้ยังอาจต้องรันคิวรีใหม่ จึงไม่ควรกล่าวว่ามีแคชแล้วไม่ต้องคำนวณอีกเลย

**คำเกี่ยวข้อง:** Publish-Time Optimization · User Session / Client / Browser · Baseline / none / +prep / +cache / +most

**อ้างอิงบริบท:** §4–5 · PDF หน้า 3–4

#### User Session / Client / Browser

**คำอ่าน:** ยูเซอร์ เซสชัน · ไคลเอนต์ · เบราว์เซอร์

**ความหมาย:** เซสชันคือช่วงการใช้งานหนึ่งช่วง ไคลเอนต์คือฝั่งที่ขอและใช้บริการ ในงานนี้คือระบบแสดงภาพที่ทำงานในเบราว์เซอร์

**ที่มาของแนวคิด:** Client–Server แบ่งบทบาทฝ่ายขอบริการกับฝ่ายให้บริการ เบราว์เซอร์มีหน้าที่มากกว่าเปิดไฟล์ภาพ เพราะรัน JavaScript และฐานข้อมูลได้ด้วย

**เหตุที่เกี่ยวข้อง:** ทรัพยากรที่คำนวณไว้ใช้ซ้ำข้ามเซสชันได้ จึงลดงานซ้ำที่แต่ละไคลเอนต์ต้องทำ

**ตัวอย่างใช้งาน:** เปิดแดชบอร์ดจากเครื่องสองเครื่อง แต่ละเครื่องมีสถานะรันไทม์ของตนเอง ไม่ควรสันนิษฐานว่าแคชในหน่วยความจำของเครื่องแรกแชร์ไปเครื่องที่สอง

**คำเกี่ยวข้อง:** Network Transfer / Local Server / WAN · Query Result Cache / Cache · DuckDB-WASM / WebAssembly

**อ้างอิงบริบท:** §1, §3.5, §4.1 · PDF หน้า 1–3

ไม่ ผลทดลองอยู่บน Mosaic กับภาพห้ารูปแบบและเงื่อนไขที่ระบุใน §5

## สไลด์ 2 · ที่มา ปัญหาความหน่วง และตัวชี้วัด

**เป้าหมาย:** แยกสามปัญหาฝั่งซ้ายออกจากสามตัวชี้วัดฝั่งขวา และกำหนดจุดเริ่ม–จุดจบของเวลาได้

**พื้นฐานก่อนอ่าน:** ทบทวนความต่างระหว่างข้อมูล ผลคิวรี ภาพ และระบบรับอินพุตจากสไลด์ 1

### ลำดับอ่านภาพ

- **ซ้ายบน: คำนวณซ้ำบนเบราว์เซอร์:** อธิบายห่วงโซ่โหลดข้อมูล → รันคิวรี → วาดภาพ ก่อนบอกว่าข้อมูลมากทำให้งานหนักขึ้น
- **ซ้ายกลาง: Cold Start:** ชี้ว่าแคชแบบสร้างระหว่างใช้งานต้องคำนวณอย่างน้อยก่อนมีผลให้ใช้ซ้ำ
- **ซ้ายล่าง: ภาพมาแต่ยังไม่พร้อม:** แยกการมองเห็นจากการเริ่มคอมโพเนนต์และส่วนรับการเลือก
- **ขวาจากบนลงล่าง: TTR → TTA → SC:** TTR วัดจุดภาพครบ TTA วัดจุดพร้อมรับอินพุต SC วัดขนาดชุดทรัพยากรที่เผยแพร่

### เหตุใด runtime cache ยังมีช่องว่างตอนเปิดเว็บ [บทความ]

แคชผลคิวรีเก็บคำตอบที่คำนวณแล้ว ถ้ายังไม่มีคำตอบ คำขอแรกต้องทำงานจริงก่อน ส่วนคำขอที่ตรงกันภายหลังอาจใช้ผลเดิมได้ ความเร็วตอนกลับมาโต้ตอบจึงไม่ใช่ความเร็วตอนเริ่มด้วยแคชว่าง
§2.2 มองว่าบางงานวิเคราะห์เฉพาะกิจต้องเริ่มทันทีโดยไม่รอเตรียม แต่แดชบอร์ดที่เผยแพร่ให้หลายเซสชันอาจยอมให้เตรียมก่อนเปิดได้ งานนี้เลือกศึกษาช่องทางหลัง ไม่ได้กล่าวว่าการเตรียมล่วงหน้าเหมาะกับทุกบริบท

หลักฐาน/ขอบเขต: §1, §2.2 · PDF หน้า 1–2

### วาดเส้นเวลาหนึ่งเส้นแล้วตั้งหมุดสองจุด [พื้นฐาน]

ตั้ง t0 เมื่อเริ่มขอหน้าเว็บ หมุดแรกอยู่เมื่อภาพข้อมูลครบ หมุดที่สองอยู่เมื่อระบบพร้อมรับอินพุต TTR กับ TTA ต่างเป็นเวลานับจากจุดเริ่ม มิใช่เอา TTA มานับต่อจาก TTR
ถ้าภาพครบที่ 800 ms และพร้อมกรองที่ 1,400 ms จะได้ TTR 800 ms กับ TTA 1,400 ms ไม่ใช่ TTA 600 ms ตัวเลขชุดนี้เป็นตัวอย่างสอนนิยามเท่านั้น ห้ามอ้างว่าเป็นผล Figure 3

### FCP กับ TTI เป็นคำเทียบเคียง ไม่ใช่ชื่อใหม่ของผลทดลอง [บทความ]

บทความเปรียบ TTR กับ FCP แต่ระบุชัดว่า TTR ต้องให้ภาพข้อมูลทั้งหมดปรากฏ ไม่ใช่เนื้อหาใดก็ได้ ถ้าชื่อเว็บขึ้นก่อนชาร์ต ชื่อเว็บที่ขึ้นไม่ใช่จุดจบ TTR
TTA เทียบแนวคิดความพร้อมโต้ตอบกับ TTI การอ้างตัวเลขงานนี้ต้องใช้ชื่อ TTA เพราะไม่ได้ยืนยันว่าใช้เกณฑ์วัด TTI ของเครื่องมือเว็บอื่นตรงกันทุกข้อ

หลักฐาน/ขอบเขต: §2.3, §3.1 · PDF หน้า 2

### SC นับอะไรและไม่นับอะไร [บทความ]

SC คือขนาดชุดทรัพยากรที่เผยแพร่ครบทั้งข้อมูลและสิ่งที่คำนวณไว้ ไม่ใช่เฉพาะภาพเริ่มต้น และค่าการเพิ่มใน Table 1 เป็นการเทียบกับ none
ขนาดที่เก็บบนระบบเผยแพร่อาจส่งผลต่อเวลารับส่งและหน่วยความจำ แต่ SC ไม่ได้เท่ากับ peak RAM ไม่ใช่ใบเรียกเก็บเงิน และไม่ใช่จำนวนไบต์ที่ดาวน์โหลดต่อเซสชันโดยอัตโนมัติ ต้องวัดต้นทุนเหล่านั้นแยก

### การลดเวลาเฉลี่ยต้องบอกฐานเปรียบเทียบ [พื้นฐาน]

สูตรอ่านง่ายคือ (ค่าหลัง − ค่าฐาน) ÷ ค่าฐาน ×100 ถ้าค่าฐาน 1,000 ms และเหลือ 200 ms การเปลี่ยนแปลงคือ −80% เครื่องหมายลบของเวลาแสดงว่ารอสั้นลง
ส่วนพื้นที่ที่เพิ่มจาก 100 เป็น 120 MB คือ +20% เครื่องหมายบวกบอกต้นทุนมากขึ้น ไม่ใช่ผลเสียทุกกรณี ต้องพิจารณาว่าประโยชน์คุ้มต้นทุนหรือไม่

### เปิดแดชบอร์ดเดียวกันสองสถานะ [ตัวอย่างพื้นฐาน]

สถานะ A มีภาพขึ้นแล้วแต่ตัวกรองยังไม่ตอบสนอง จึงผ่านหมุด TTR แต่ยังไม่ผ่านหมุด TTA สถานะ B มีทั้งภาพและระบบตัวกรองพร้อม จึงผ่านทั้งสองหมุด
การสอนด้วยสองสถานะนี้ช่วยตอบคำถามว่าเหตุใดลด TTR มากแต่ TTA ลดน้อยได้ โดยไม่ต้องอธิบายสมการซับซ้อน

t0: เริ่มคำขอ → 800 ms: ภาพครบ → TTR → 1,400 ms: พร้อมอินพุต → TTA

### ศัพท์ประจำสไลด์

#### Run-Time / Runtime

**คำอ่าน:** รัน-ไทม์

**ความหมาย:** ช่วงที่ระบบทำงานเมื่อมีเซสชันใช้งาน รวมการโหลดข้อมูล รันคิวรี วาดภาพ และรับการโต้ตอบ

**ที่มาของแนวคิด:** Run คือทำงาน Time คือช่วงเวลา ต่างจากช่วงเตรียมเผยแพร่ตรงที่ผู้ใช้งานกำลังรอผลอยู่

**เหตุที่เกี่ยวข้อง:** Baseline none คำนวณทุกอย่างตอนรันไทม์ การปรับปรุงไม่ได้ตัดรันไทม์ทิ้ง เพราะภาพโต้ตอบยังต้องเริ่มคอมโพเนนต์

**ตัวอย่างใช้งาน:** การกดตัวกรองที่ไม่เคยเตรียมผลไว้ยังอาจต้องรันคิวรีใหม่ จึงไม่ควรกล่าวว่ามีแคชแล้วไม่ต้องคำนวณอีกเลย

**คำเกี่ยวข้อง:** Publish-Time Optimization · User Session / Client / Browser · Baseline / none / +prep / +cache / +most

**อ้างอิงบริบท:** §4–5 · PDF หน้า 3–4

#### Cold Start

**คำอ่าน:** โคลด์ สตาร์ต

**ความหมาย:** การเริ่มระบบในสถานะที่ยังไม่มีผลลัพธ์หรือโครงสร้างเร่งความเร็วที่ต้องใช้

**ที่มาของแนวคิด:** Cold สื่อว่ายังไม่อุ่นเครื่อง เช่น แคชว่าง จึงต้องสร้างผลก่อน เรียกสภาวะที่พร้อมใช้ผลเดิมว่า warm

**เหตุที่เกี่ยวข้อง:** Runtime cache ช่วยหลังสร้างแคชแล้ว แต่ยังไม่ช่วยเซสชันที่ต้องสร้างใหม่ การคำนวณช่วงเผยแพร่เติมส่วนที่ขาดนี้

**ตัวอย่างใช้งาน:** คิวรีรวมข้อมูลล้านแถวครั้งแรกช้า ครั้งถัดไปอาจคืนจากแคชได้เร็ว ทั้งนี้ cold ในงานนี้ไม่เท่ากับคำ cold start ของ serverless ทุกกรณี

**คำเกี่ยวข้อง:** Query Result Cache / Cache · User Session / Client / Browser · Run-Time / Runtime

**อ้างอิงบริบท:** §2.2–3.3 · PDF หน้า 2

#### Query Result Cache / Cache

**คำอ่าน:** คิวรี รีซัลต์ แคช · แคช

**ความหมาย:** ที่เก็บผลคิวรีซึ่งเคยคำนวณแล้ว เพื่อใช้ซ้ำเมื่อมีคำขอที่ตรงกัน

**ที่มาของแนวคิด:** Cache เน้นการนำผลเดิมกลับมาใช้ ลดงานคำนวณ ไม่ใช่ชื่อรูปแบบไฟล์หรือฐานข้อมูลชนิดหนึ่ง

**เหตุที่เกี่ยวข้อง:** Publisher เตรียม result cache แล้วเติมให้ Coordinator ตอนเริ่มระบบ ต่างจากรอสร้างระหว่างใช้งาน

**ตัวอย่างใช้งาน:** ผลยอดรวมตามเดือนที่เตรียมไว้ตอบคิวรีเดิมได้ แต่เมื่อข้อมูลเปลี่ยนต้องจัดการความถูกต้องของผลเก่า

**คำเกี่ยวข้อง:** Pre-computation / Pre-aggregation · Pre-aggregated Materialized View · Data Freshness / Cache Invalidation

**อ้างอิงบริบท:** §3.3, §4.3 · PDF หน้า 2–3

#### TTR — Time-to-Render

**คำอ่าน:** ที-ที-อาร์ · ไทม์-ทู-เรนเดอร์

**ความหมาย:** เวลาตั้งแต่ส่งคำขอหน้าเว็บจนภาพข้อมูลปรากฏครบถ้วน

**ที่มาของแนวคิด:** Render คือสร้างผลที่มองเห็นได้ ตัวชี้วัดนี้จับจุดที่ภาพพร้อมสำหรับการอ่าน ไม่จับเพียงข้อความแรกที่ปรากฏ

**เหตุที่เกี่ยวข้อง:** ภาพล่วงหน้าลดงานที่กั้นการมองเห็น จึงลด TTR ได้มากกว่า TTA ในผลชุดรวม

**ตัวอย่างใช้งาน:** กำหนด t0 ตอนขอหน้าและ tภาพครบ แล้ว TTR = tภาพครบ − t0 ตัวอย่างนาฬิกาจำลอง 0→800 ms ไม่ใช่ค่าของ Figure 3

**คำเกี่ยวข้อง:** Rendering / SVG / Raster / Canvas · FCP — First Contentful Paint · TTA — Time-to-Activation

**อ้างอิงบริบท:** §3.1 · PDF หน้า 2

#### TTA — Time-to-Activation

**คำอ่าน:** ที-ที-เอ · ไทม์-ทู-แอ็กทิเวชัน

**ความหมาย:** เวลาจนระบบพร้อมตอบสนองอินพุต เช่น เลือกช่วง กรอง หรือซูม

**ที่มาของแนวคิด:** Activation คือทำให้ระบบพร้อมใช้งาน เวลานี้ไม่เท่ากับเวลาประมวลผลทุกการคลิกหลังเปิดเว็บแล้ว

**เหตุที่เกี่ยวข้อง:** แคชช่วยลดงานก่อนพร้อมโต้ตอบ แต่ภาพล่วงหน้ายังต้อง hydration จึงช่วย TTA เพิ่มเพียงเล็กน้อย

**ตัวอย่างใช้งาน:** ถ้าภาพครบที่ 800 ms แต่ตัวกรองพร้อมที่ 1,400 ms ค่า TTR กับ TTA ต่างกัน ตัวเลขเป็นตัวอย่างสอนนิยาม

**คำเกี่ยวข้อง:** TTR — Time-to-Render · TTI — Time to Interactive · Client Hydration · Activation / Event / Input

**อ้างอิงบริบท:** §3.1, §5 · PDF หน้า 2, 4

#### SC — Storage Cost / Deployment Footprint

**คำอ่าน:** เอส-ซี · สตอเรจ คอสต์ · ดีพลอยเมนต์ ฟุตพรินต์

**ความหมาย:** ขนาดทรัพยากรทั้งหมดที่เผยแพร่ เช่น ข้อมูล สคริปต์ ภาพ และผลคำนวณล่วงหน้า

**ที่มาของแนวคิด:** Cost ในชื่อหมายถึงต้นทุนด้านพื้นที่ ไม่ได้รายงานเป็นค่าใช้จ่ายเงิน Footprint คือขนาดรวมที่ต้องเก็บไว้เพื่อเผยแพร่

**เหตุที่เกี่ยวข้อง:** บทความเปรียบเทียบการเปลี่ยนแปลง SC กับ none เพื่อเห็นต้นทุนของการเร่งความเร็ว

**ตัวอย่างใช้งาน:** ถ้าชุดเดิม 100 MB และเพิ่ม 21.2% ขนาดใหม่คือ 121.2 MB เป็นตัวอย่างคำนวณ ไม่ใช่ขนาดจริงที่บทความรายงาน

**คำเกี่ยวข้อง:** Trade-off / Benchmark / Threats to Validity · Network Transfer / Local Server / WAN · Pre-computation / Pre-aggregation

#### FCP — First Contentful Paint

**คำอ่าน:** เอฟ-ซี-พี · เฟิร์สต์ คอนเทนต์ฟูล เพนต์

**ความหมาย:** ตัวชี้วัดเว็บที่สนใจเมื่อมีเนื้อหาแรกปรากฏ TTR ของบทความกำหนดให้ภาพข้อมูลครบถ้วนแล้ว

**ที่มาของแนวคิด:** Paint คือการแสดงเนื้อหาบนหน้าจอ First เน้นครั้งแรก ความคล้ายด้านเวลารอไม่ได้ทำให้สองนิยามเท่ากัน

**เหตุที่เกี่ยวข้อง:** สไลด์ใช้ FCP เป็นสะพานอธิบาย แต่ห้ามเรียกผล TTR ของงานนี้ว่าผล FCP

**ตัวอย่างใช้งาน:** ชื่อเว็บอาจปรากฏก่อนชาร์ตครบ การเห็นชื่อจึงยังไม่เป็นหลักฐานว่าการแสดงภาพข้อมูลพร้อมแล้ว

**คำเกี่ยวข้อง:** TTR — Time-to-Render · Rendering / SVG / Raster / Canvas

**อ้างอิงบริบท:** §2.3, §3.1 · PDF หน้า 2

#### TTI — Time to Interactive

**คำอ่าน:** ที-ที-ไอ · ไทม์ ทู อินเทอร์แอ็กทีฟ

**ความหมาย:** แนวคิดความพร้อมโต้ตอบในเว็บที่บทความใช้เทียบเคียง TTA ไม่ใช่การยืนยันว่าใช้วิธีวัด TTI แบบเดียวกัน

**ที่มาของแนวคิด:** Interactive หมายถึงรับการโต้ตอบได้ การวัดจริงต้องระบุเงื่อนไขความพร้อม งานนี้กำหนด TTA สำหรับภาพข้อมูล

**เหตุที่เกี่ยวข้อง:** ช่วยอธิบายว่าโหลดภาพเสร็จยังไม่จบงานของระบบโต้ตอบ

**ตัวอย่างใช้งาน:** การคลิกตัวกรองได้และระบบพร้อมประมวลผลเป็นคนละเหตุการณ์กับเห็นภาพครั้งแรก

**คำเกี่ยวข้อง:** TTA — Time-to-Activation · Client Hydration · input

**อ้างอิงบริบท:** §2.3, §3.1 · PDF หน้า 2

#### Latency / Perceived Latency / Interface Lag

**คำอ่าน:** เลเทนซี · เพอร์ซีฟด์ เลเทนซี · อินเทอร์เฟซ แล็ก

**ความหมาย:** Latency คือช่วงเวลารอจนเหตุการณ์ที่สนใจเกิดขึ้น Perceived Latency เน้นเวลารอที่ผู้ใช้งานรับรู้ Interface Lag คือความหน่วงของส่วนติดต่อ

**ที่มาของแนวคิด:** คำเหล่านี้ระบุประสบการณ์การรอ แต่ต้องกำหนดจุดเริ่มและจุดจบก่อนวัด มิฉะนั้นตัวเลขจากคนละงานเทียบกันไม่ได้

**เหตุที่เกี่ยวข้อง:** งานนี้แยกการรอภาพออกจากการรอระบบพร้อมรับอินพุต ไม่ใช้ความเร็วเว็บเป็นตัวเลขเดียว

**ตัวอย่างใช้งาน:** ภาพเปิดมาแล้วแต่ตัวกรองไม่ทำงานยังสร้างความหน่วง การส่งภาพเร็วเพียงอย่างเดียวจึงไม่ตอบทุกปัญหา

**คำเกี่ยวข้อง:** TTR — Time-to-Render · TTA — Time-to-Activation · Network Transfer / Local Server / WAN

**อ้างอิงบริบท:** §1–2.1, §3.1 · PDF หน้า 1–2

#### Network Transfer / Local Server / WAN

**คำอ่าน:** เน็ตเวิร์ก ทรานส์เฟอร์ · โลคัล เซิร์ฟเวอร์ · แวน

**ความหมาย:** Network transfer คือการส่งทรัพยากรระหว่างระบบ Local server คือเซิร์ฟเวอร์ใกล้สภาพแวดล้อมทดลอง WAN คือเครือข่ายบริเวณกว้าง

**ที่มาของแนวคิด:** เวลาคำนวณกับเวลารับส่งเป็นคนละต้นทุน การเพิ่มไฟล์ล่วงหน้าอาจลดคำนวณแต่เพิ่มข้อมูลที่ต้องส่ง

**เหตุที่เกี่ยวข้อง:** Figure 4 แยกส่วน Network ผลทดลองผ่าน local server จึงไม่รับรองผลบนเครือข่ายมือถือหรือ WAN

**ตัวอย่างใช้งาน:** ชุดแคชใหญ่ที่โหลดเร็วบนเครื่องทดลองอาจโหลดช้าบนเครือข่ายจำกัด ต้องวัดใหม่ ไม่ใช้ SC แทนปริมาณส่งทุกเซสชันโดยตรง

**คำเกี่ยวข้อง:** SC — Storage Cost / Deployment Footprint · Latency / Perceived Latency / Interface Lag · CDN / Edge / IoT Sensor Dashboard

**อ้างอิงบริบท:** Figure 4, §5 · PDF หน้า 4; WAN เป็นพื้นฐานประกอบ

#### Rendering / SVG / Raster / Canvas

**คำอ่าน:** เรนเดอริง · เอส-วี-จี · แรสเตอร์ · แคนวาส

**ความหมาย:** Rendering คือแปลงข้อมูลและข้อกำหนดเป็นภาพ SVG เก็บรูปร่างแบบเวกเตอร์ ส่วน raster เก็บภาพเป็นพิกเซล Canvas เป็นพื้นผิววาดภาพในเว็บ

**ที่มาของแนวคิด:** ภาพที่วาดเสร็จกับส่วนประกอบที่คำนวณภาพใหม่ได้มีบทบาทต่างกัน การส่งภาพอย่างเดียวไม่ทำให้ตัวกรองทำงาน

**เหตุที่เกี่ยวข้อง:** §3.4 ยกเวกเตอร์และบิตแมปเป็นรูปแบบภาพล่วงหน้า ส่วนกรณี property/gaia/taxis มีภาพ raster

**ตัวอย่างใช้งาน:** ภาพกราฟที่เปิดได้เร็วเป็นผลการเรนเดอร์ ส่วนชาร์ตที่เลือกช่วงแล้วคำนวณใหม่ได้ต้องมีตรรกะและข้อมูลเพิ่มเติม

**คำเกี่ยวข้อง:** Pre-rendering / Initial Pre-rendering · Client Hydration · Static View / Interactive View / Component

#### Activation / Event / Input

**คำอ่าน:** แอ็กทิเวชัน · อีเวนต์ · อินพุต

**ความหมาย:** Activation คือความพร้อมทำงาน Event คือเหตุการณ์ เช่น คลิกหรือเปลี่ยนค่า Input คือค่าหรือการกระทำที่ป้อนให้ระบบ

**ที่มาของแนวคิด:** การมีปุ่มในภาพกับการมีตรรกะรับปุ่มเป็นคนละเงื่อนไข ภาพปุ่มอย่างเดียวไม่ประมวลผลเหตุการณ์

**เหตุที่เกี่ยวข้อง:** Figure 4 แยกส่วน Hydration กับ Activation ส่วน TTA เป็นเวลาจากเริ่มจนพร้อมรับอินพุตทั้งหมด

**ตัวอย่างใช้งาน:** การเลื่อน slider ทำให้คิวรีเปลี่ยน ต้องเริ่มส่วนที่รับค่าและส่งคำขอให้ครบก่อน

**คำเกี่ยวข้อง:** TTA — Time-to-Activation · Client Hydration · Virtual DOM / Interaction Simulation

#### User Session / Client / Browser

**คำอ่าน:** ยูเซอร์ เซสชัน · ไคลเอนต์ · เบราว์เซอร์

**ความหมาย:** เซสชันคือช่วงการใช้งานหนึ่งช่วง ไคลเอนต์คือฝั่งที่ขอและใช้บริการ ในงานนี้คือระบบแสดงภาพที่ทำงานในเบราว์เซอร์

**ที่มาของแนวคิด:** Client–Server แบ่งบทบาทฝ่ายขอบริการกับฝ่ายให้บริการ เบราว์เซอร์มีหน้าที่มากกว่าเปิดไฟล์ภาพ เพราะรัน JavaScript และฐานข้อมูลได้ด้วย

**เหตุที่เกี่ยวข้อง:** ทรัพยากรที่คำนวณไว้ใช้ซ้ำข้ามเซสชันได้ จึงลดงานซ้ำที่แต่ละไคลเอนต์ต้องทำ

**ตัวอย่างใช้งาน:** เปิดแดชบอร์ดจากเครื่องสองเครื่อง แต่ละเครื่องมีสถานะรันไทม์ของตนเอง ไม่ควรสันนิษฐานว่าแคชในหน่วยความจำของเครื่องแรกแชร์ไปเครื่องที่สอง

**คำเกี่ยวข้อง:** Network Transfer / Local Server / WAN · Query Result Cache / Cache · DuckDB-WASM / WebAssembly

**อ้างอิงบริบท:** §1, §3.5, §4.1 · PDF หน้า 1–3

#### Baseline / none / +prep / +cache / +most

**คำอ่าน:** เบสไลน์ · นัน · พลัสเพรป · พลัสแคช · พลัสโมสต์

**ความหมาย:** Baseline คือกรณีอ้างอิง none ในงานนี้ ระดับอื่นเพิ่มการปรับปรุงแบบสะสม ไม่ใช่เปิดเพียงกลยุทธ์เดียว

**ที่มาของแนวคิด:** เครื่องหมายบวกสื่อการเพิ่มจากระดับก่อน +cache รวม prep และแคช +most รวมภาพเริ่มต้นด้วย

### จุดที่มักอธิบายผิด

- อย่าเรียก Cold Start ว่าผู้ใช้งานคนแรกของทั้งเว็บไซต์เสมอ ประเด็นคือสถานะทรัพยากรของสภาพแวดล้อมที่เริ่ม
- อย่าใช้คำว่าเว็บเร็วขึ้นแทนตัวชี้วัดทั้งสามโดยไม่กำหนดความหมาย
- อย่าอ่าน TTA เป็นเวลารอของทุกการคลิกหลังเปิดหน้าแล้ว

### คำถามตรวจความเข้าใจ

**เห็นภาพครบแล้วตัวกรองยังไม่พร้อม เรียกผ่านตัวชี้วัดใด?**

ผ่าน TTR แต่ยังไม่ผ่าน TTA

**โหลดข้อมูลมากขึ้นต้องทำให้ SC มากขึ้นเสมอหรือไม่?**

ไม่ SC กับปริมาณส่งจริงคนละตัวชี้วัด เช่นการจัดชุดเผยแพร่กับการเลือกโหลดเฉพาะบางทรัพยากรอาจต่างกัน

**แคชที่ช่วยการคลิกครั้งที่สองพิสูจน์ว่าเปิดหน้าแรกเร็วแล้วหรือไม่?**

ไม่ คำขอแรกอาจยังต้องสร้างแคชก่อน นี่เป็นเหตุผลที่ศึกษาการเตรียมช่วงเผยแพร่

### ข้อกำหนดคือแผนของภาพ ไม่ใช่ภาพสำเร็จ [บทความ]

Mosaic ใช้ declarative specification ระบุข้อมูล มุมมอง และการโต้ตอบ Publisher ในงานนี้อ่านข้อกำหนด YAML แล้วสร้าง AST โครงสร้างต้นไม้ช่วยให้รู้ว่าส่วนไหนเตรียมข้อมูล ส่วนไหนวาด และส่วนไหนรับอินพุต
การ rewrite จึงเป็นการแก้ความหมายของโหนดที่ต้องใช้ทรัพยากรใหม่อย่างเจาะจง ไม่ใช่ค้นคำ SQL แล้วแทนข้อความทั่วไฟล์โดยไม่รู้บริบท จุดมุ่งหมายคือรักษาภาพและการโต้ตอบเดิมขณะเปลี่ยนเส้นทางเข้าถึงข้อมูล

### เหตุใดอ่าน AST อย่างเดียวไม่พอ [บทความ]

### DuckDB คำนวณก่อน ส่วน DuckDB-WASM ใช้ตอนทดลอง [บทความ]

Publisher ใช้ in-process DuckDB เพื่อรันคิวรีเตรียม คิวรีเริ่มต้น และผลรวม จากนั้นบันทึกผลเป็น deployable assets ผลที่เก็บจริงคือคำตอบและโครงสร้างช่วยคำนวณ ไม่ใช่เพียงข้อความ SQL
Mosaic รองรับการรันคิวรีในเบราว์เซอร์ เซิร์ฟเวอร์ใกล้เครื่อง หรือฐานข้อมูลระยะไกลได้ ส่วนการทดลอง §5 ใช้ DuckDB-WASM ในเบราว์เซอร์ ต้องแยกความยืดหยุ่นของสถาปัตยกรรมออกจากสภาพแวดล้อมที่วัดจริง

หลักฐาน/ขอบเขต: §4.1–4.2, §5 · PDF หน้า 3–4

### Result cache กับ materialized aggregate ไม่ใช่สิ่งเดียวกัน [พื้นฐานเชื่อมบทความ]

Result cache เก็บคำตอบคิวรีที่คำนวณแล้ว ส่วน materialized aggregate เก็บผลสรุปที่คิวรีรองรับนำไปใช้ได้ ทั้งคู่เลี่ยงงานอ่านและคำนวณซ้ำ แต่มีวิธีนำกลับมาใช้และขอบเขตคำถามต่างกัน
ตัวอย่างผลรวมจำนวนเที่ยวบินตามวันและสนามบินอาจตอบจำนวนตามวันโดยรวมข้ามสนามบินได้ แต่ไม่รับรองว่าจะตอบทุกคำถามของข้อมูลดิบ เช่น รายละเอียดของเที่ยวบินแต่ละรายการ ตัวอย่างนี้สอนความต่าง ไม่ใช่รูปแบบแคชจริงที่ถอดจากโค้ด

หลักฐาน/ขอบเขต: บทบาทจริง §3.3, §4.3 · PDF หน้า 2–3; ตัวอย่างเป็นพื้นฐาน

### Transparent optimization กับ explicit rewrite [บทความ]

Coordinator ควบคุมการสร้างและรันคิวรี จึงโหลด result cache และ materialized views แล้วใช้ทรัพยากรแทนคำนวณได้โดยโปร่งใสต่อข้อกำหนดภาพ ไม่ต้องแก้ทุกมุมมองให้เรียกแคชเอง
แต่ถ้าเปลี่ยนจากคิวรีเตรียมข้อมูลมาอ่านผลเตรียมสำเร็จ เส้นทางเข้าถึงข้อมูลเปลี่ยนจริง Publisher จึง rewrite โหนดเตรียมข้อมูล สคริปต์ที่สร้างเพิ่มจะเติมแคช ฐานข้อมูล และเริ่ม interactive components เมื่อจำเป็น

หลักฐาน/ขอบเขต: §4.2–4.3 · PDF หน้า 3

### จำแนกสามกลุ่มจากสิ่งที่ได้ ไม่ใช่จากชื่อไฟล์ [บทความ]

Data preparation ได้ข้อมูลที่คัดหรือแปลงแล้ว Pre-computation ได้ผลคิวรีกับผลรวมเร่งความเร็ว Pre-rendering ได้ภาพเริ่มต้นที่วาดแล้ว สิ่งเหล่านี้อาจต้องโหลดร่วมกันสำหรับภาพโต้ตอบ
PDF ไม่ระบุว่าทรัพยากรทุกชิ้นบันทึกเป็น Parquet หรือ Arrow จึงไม่ควรสอนว่าระบบนี้ใช้รูปแบบสองชนิดนั้นทั้งหมด หากยก JSON หรือไฟล์ตารางเพื่ออธิบายต้องระบุว่าเป็นตัวอย่างพื้นฐาน

หลักฐาน/ขอบเขต: §3.2–3.4, §4.2–4.3 · PDF หน้า 2–3

### จากคิวรีนับเที่ยวบินสู่ทรัพยากรใช้ซ้ำ [ตัวอย่างพื้นฐาน]

สมมติชาร์ตแสดงจำนวนเที่ยวบินตามวัน และมีตัวกรองสนามบิน Publisher ต้องรู้ทั้งคิวรีภาพเริ่มต้นและคิวรีที่เกิดเมื่อเปลี่ยนตัวกรอง จึงจำลองอินพุตก่อนคำนวณผลที่เกี่ยวข้อง
ก่อนเตรียม: ข้อกำหนดสั่งให้คำนวณจากข้อมูลดิบ หลังเตรียม: บางโหนดอ่านข้อมูลพร้อมใช้ Coordinator ได้ผลคิวรีกับผลรวม และเบราว์เซอร์ได้ภาพเริ่มต้น SQL ด้านล่างเป็นตัวอย่างแนวคิด ไม่ใช่คำสั่งจริงของ Publisher

AST: รู้ข้อมูล/ภาพ/อินพุต → Virtual DOM: กระตุ้นคิวรี → DuckDB: คำนวณและเก็บผล → Rewrite + JS: โหลดผลและเปิดโต้ตอบ

```sql
SELECT day, COUNT(*) AS flights
FROM flights
GROUP BY day;

-- Conceptual pipeline, not the Publisher API:
parse specification -> simulate inputs -> collect queries
compute assets -> rewrite preparation nodes -> emit runtime JS
```

### ศัพท์ประจำสไลด์

#### Mosaic / Mosaic Publisher / Coordinator

**คำอ่าน:** โมเซอิก · โมเซอิก พับลิชเชอร์ · โคออร์ดิเนเตอร์

**ความหมาย:** Mosaic เป็นสถาปัตยกรรมแสดงภาพข้อมูล Coordinator จัดการคิวรีและการเชื่อมมุมมอง ส่วน Publisher เป็นเครื่องมือเตรียมทรัพยากรก่อนเผยแพร่

**ที่มาของแนวคิด:** คำว่า coordinator สื่อบทบาทผู้ประสานงาน การแยกตัวกลางออกจากมุมมองทำให้เติมแคชและฐานข้อมูลได้โดยไม่แก้ทุกชาร์ต

**เหตุที่เกี่ยวข้อง:** Publisher เป็นกลไกที่ผู้วิจัยพัฒนาในงานนี้บนสถาปัตยกรรม Mosaic ที่มีอยู่แล้ว

**ตัวอย่างใช้งาน:** หลายชาร์ตส่งคำขอผ่านตัวกลาง ตัวกลางอาจคืนผลจากแคชหรือใช้ผลรวมใน DuckDB แทนคำนวณซ้ำ

**คำเกี่ยวข้อง:** Query / SQL / Query Materialization · AST — Abstract Syntax Tree / AST Rewriting · DuckDB / In-Process Database · Cross-filtering / Linked Views / Brushing / Confidence Interval / Regression Fit

**อ้างอิงบริบท:** §4.1–4.3 · PDF หน้า 3

#### Declarative Specification / YAML

**คำอ่าน:** ดีแคลเรทีฟ สเปซิฟิเคชัน · แยมเมิล

**ความหมาย:** ข้อกำหนดที่บอกว่าต้องการข้อมูล ภาพ และการโต้ตอบแบบใด YAML เป็นรูปแบบข้อความที่ใช้เขียนข้อกำหนดในงานนี้

**ที่มาของแนวคิด:** Declarative เน้นบอกสิ่งที่ต้องการ ต่างจากเขียนทุกขั้นตอนการทำงานเอง ระบบต้องแปลข้อกำหนดไปเป็นการคำนวณจริง

**เหตุที่เกี่ยวข้อง:** โครงสร้างที่อ่านได้ช่วยให้ Publisher วิเคราะห์และแก้แหล่งข้อมูลแบบเจาะจง

**ตัวอย่างใช้งาน:** ข้อกำหนดว่าชาร์ตใช้วันที่กับจำนวนเที่ยวบินช่วยระบุคอลัมน์และคิวรีที่จำเป็น ตัวอย่างข้อความในบทเรียนเป็นรหัสจำลอง

**คำเกี่ยวข้อง:** AST — Abstract Syntax Tree / AST Rewriting · Static View / Interactive View / Component · input

**อ้างอิงบริบท:** §4.1–4.2 · PDF หน้า 3

#### AST — Abstract Syntax Tree / AST Rewriting

**คำอ่าน:** เอ-เอส-ที · แอบสแทร็กต์ ซินแท็กซ์ ทรี · รีไรทิง

**ความหมาย:** โครงสร้างต้นไม้แทนส่วนสำคัญของข้อกำหนด การ rewrite คือแก้โหนดที่ต้องเปลี่ยน เช่น แทนคิวรีเตรียมด้วยอ้างอิงผลที่คำนวณแล้ว

**ที่มาของแนวคิด:** Syntax คือโครงสร้างภาษา Abstract หมายถึงละรายละเอียดรูปแบบข้อความที่ไม่จำเป็น Tree คือส่วนประกอบซ้อนเป็นกิ่ง การแก้ต้นไม้จึงตรงส่วนกว่าแทนคำดิบแบบสุ่ม

**เหตุที่เกี่ยวข้อง:** การเตรียมที่เปลี่ยนวิธีเข้าถึงข้อมูลต้อง rewrite ต่างจากเติมแคชที่ Coordinator ใช้ได้โดยโปร่งใส

**ตัวอย่างใช้งาน:** โหนดเดิมเตรียมตารางด้วยคิวรี โหนดใหม่อ่านผลเตรียมสำเร็จ ต้องรักษาความหมายของภาพ ไม่ใช่แก้ชื่อไฟล์อย่างเดียว

**คำเกี่ยวข้อง:** Declarative Specification / YAML · Query / SQL / Query Materialization · Mosaic / Mosaic Publisher / Coordinator

**อ้างอิงบริบท:** §4.1–4.3 · PDF หน้า 3

#### Virtual DOM / Interaction Simulation

**คำอ่าน:** เวอร์ชวล ดอม · อินเทอร์แอ็กชัน ซิมูเลชัน

**ความหมาย:** สภาพแวดล้อมแทนองค์ประกอบหน้าเว็บที่ใช้กระตุ้นอินพุตและตรวจคิวรีในช่วงเผยแพร่

**ที่มาของแนวคิด:** DOM คือโครงสร้างองค์ประกอบเอกสารในเว็บ Virtual ในที่นี้เน้นสภาพแวดล้อมจำลองสำหรับรันอินพุต ไม่ใช่หลักฐานว่าใช้ React

**เหตุที่เกี่ยวข้อง:** คิวรีบางชุดจะเกิดเมื่อเลือกช่วงเท่านั้น Publisher จึงจำลองการโต้ตอบเพื่อค้นพบงานที่ต้องเตรียม

**ตัวอย่างใช้งาน:** จำลองการเปลี่ยนค่าตัวกรองแล้วเก็บคิวรีที่เกิดขึ้น ไม่ใช่เพียงอ่านข้อความ SQL ที่เขียนอยู่ในข้อกำหนด

**คำเกี่ยวข้อง:** input · Query / SQL / Query Materialization · AST — Abstract Syntax Tree / AST Rewriting

**อ้างอิงบริบท:** §4.2–4.3 · PDF หน้า 3

#### Query / SQL / Query Materialization

**คำอ่าน:** คิวรี · เอส-คิว-แอล · คิวรี มะทีเรียไลเซชัน

**ความหมาย:** Query คือคำขอข้อมูล SQL คือภาษาสำหรับระบุคำขอ Materialization คือคำนวณผลแล้วเก็บเป็นทรัพยากรใช้ได้จริง

**ที่มาของแนวคิด:** คำสั่งกับผลคำสั่งเป็นคนละสิ่ง เก็บข้อความ SELECT อย่างเดียวไม่ได้เลี่ยงงานอ่านและสรุปข้อมูล

**เหตุที่เกี่ยวข้อง:** Publisher รันคิวรีเตรียม โหลดเริ่มต้น และผลรวม แล้วบันทึกผลเผยแพร่

**ตัวอย่างใช้งาน:** SELECT day, COUNT(*) FROM flights GROUP BY day สื่อการนับเที่ยวบินตามวัน เป็น SQL อธิบายหลักการ ไม่ใช่คิวรีที่ยืนยันจากโค้ดผู้วิจัย

**คำเกี่ยวข้อง:** DuckDB / In-Process Database · Query Result Cache / Cache · Pre-aggregated Materialized View

**อ้างอิงบริบท:** §4.2 · PDF หน้า 3

#### DuckDB / In-Process Database

**คำอ่าน:** ดัก-ดี-บี · อิน-โพรเซส ดาตาเบส

**ความหมาย:** ฐานข้อมูลที่รันอยู่ภายในกระบวนการของโปรแกรมที่เรียกใช้งาน ในงานนี้ใช้คำนวณทรัพยากรช่วงเผยแพร่

**ที่มาของแนวคิด:** In-process แยกจากการต้องส่งคำขอไปฐานข้อมูลอีกเซิร์ฟเวอร์ทุกครั้ง เน้นตำแหน่งที่รัน ไม่ได้แปลว่าข้อมูลทุกอย่างอยู่ใน RAM เสมอ

**เหตุที่เกี่ยวข้อง:** Publisher ใช้ DuckDB สร้างผลอย่างอิสระจากสภาพแวดล้อมรันไทม์

**ตัวอย่างใช้งาน:** โปรแกรมเตรียมงานเปิดฐานข้อมูล รันคิวรี และบันทึกผล จากนั้นส่งผลไปใช้ฝั่งเบราว์เซอร์

**คำเกี่ยวข้อง:** DuckDB-WASM / WebAssembly · Query / SQL / Query Materialization · Mosaic / Mosaic Publisher / Coordinator

**อ้างอิงบริบท:** §4.1 · PDF หน้า 3

#### DuckDB-WASM / WebAssembly

**คำอ่าน:** ดัก-ดี-บี แวซึม · เว็บแอสเซมบลี

**ความหมาย:** รูปแบบที่ทำให้ DuckDB ทำงานในเบราว์เซอร์ผ่าน WebAssembly จึงประมวลผลข้อมูลฝั่งไคลเอนต์ได้

**ที่มาของแนวคิด:** WebAssembly คือรูปแบบโปรแกรมที่สภาพแวดล้อมเว็บรันได้ บทเรียนเน้นบทบาท ไม่กล่าวอ้างว่ารันเร็วกว่าทุกระบบ

**เหตุที่เกี่ยวข้อง:** การทดลองใช้ DuckDB-WASM เป็นฐานข้อมูลรองรับภาพ ฝั่งเผยแพร่ใช้ in-process DuckDB ต่างช่วงและต่างหน้าที่

**ตัวอย่างใช้งาน:** เบราว์เซอร์โหลดฐานข้อมูลและผลรวมพร้อมคิวรีภายในเครื่องได้ จึงลดการพึ่งเซิร์ฟเวอร์คิวรีในบางสถาปัตยกรรม แต่ยังมีต้นทุนโหลดและเริ่มระบบ

**คำเกี่ยวข้อง:** DuckDB / In-Process Database · User Session / Client / Browser · In-Browser OLAP

**อ้างอิงบริบท:** §4.1, §5 · PDF หน้า 3–4

#### Pre-aggregated Materialized View

**คำอ่าน:** พรีแอกกริเกเต็ด มะทีเรียไลซ์ด วิว

**ความหมาย:** ผลสรุปข้อมูลที่คำนวณแล้วเก็บไว้เป็นโครงสร้างในฐานข้อมูล เพื่อให้คิวรีบางประเภทใช้ผลเดิม

**ที่มาของแนวคิด:** View ในฐานข้อมูลคือมุมมองข้อมูล ไม่ใช่ชาร์ตบนหน้าจอ Materialized ระบุว่าผลถูกเก็บจริง Pre-aggregated ระบุว่ารวมกลุ่มไว้ก่อน

**เหตุที่เกี่ยวข้อง:** Mosaic ใช้ผลรวมตาม bins และตำแหน่งอินพุตช่วยการกรองและรวมข้อมูลใหม่

**ตัวอย่างใช้งาน:** ผลนับเที่ยวบินแยกวันกับสนามบินใช้ตอบคำถามที่เข้ากับมิตินั้นได้ แต่ไม่จำเป็นต้องตอบคำถามทุกคอลัมน์ของข้อมูลดิบ

**คำเกี่ยวข้อง:** Pre-computation / Pre-aggregation · Bin / Aggregation Dimension / Cardinality · Query Result Cache / Cache · Static View / Interactive View / Component

**อ้างอิงบริบท:** §3.3, §4.3 · PDF หน้า 2–3

#### Pre-computation / Pre-aggregation

**คำอ่าน:** พรีคอมพิวเทชัน · พรีแอกกริเกชัน

**ความหมาย:** คำนวณผลที่ต้องใช้ไว้ก่อน Pre-aggregation เน้นผลสรุป เช่น จำนวน ผลรวม หรือค่าเฉลี่ยตามกลุ่ม

**ที่มาของแนวคิด:** Pre หมายถึงก่อน Aggregation คือรวมข้อมูลหลายแถวเป็นค่ากลุ่ม งานที่เคยอ่านข้อมูลดิบจึงอาจอ่านสรุปที่เล็กกว่า

**เหตุที่เกี่ยวข้อง:** ระดับ +cache รวมทั้ง result cache และ materialized aggregates สำหรับการโต้ตอบ ไม่ได้เก็บแค่ภาพ

**ตัวอย่างใช้งาน:** ข้อมูลเที่ยวบินล้านแถวสรุปจำนวนตามวันและสนามบินแล้วใช้ผลนั้นตอบคิวรีที่รองรับ หากคำถามเปลี่ยนเกินมิติที่เตรียมไว้ยังอาจต้องอ่านข้อมูลดิบ

**คำเกี่ยวข้อง:** Query Result Cache / Cache · Pre-aggregated Materialized View · Bin / Aggregation Dimension / Cardinality

**อ้างอิงบริบท:** §3.3, §4.2, §5 · PDF หน้า 2–4

**ความหมาย:** เตรียมข้อมูลโดยเลือกคอลัมน์ที่ใช้ แปลงค่า หรือจัดรูปข้อมูลก่อนนำไปแสดง

**ที่มาของแนวคิด:** Projection ในบริบทฐานข้อมูลคือเลือกคอลัมน์ ต่างจากการฉายพิกัดแผนที่ Transformation อาจเป็นคำนวณฟิลด์หรือเชื่อมตาราง

**เหตุที่เกี่ยวข้อง:** §3.2 เสนอวิธีลดข้อมูลและคิวรี แต่ +prep ช่วยน้อยในชุดทดลองที่ไม่มีคอลัมน์เกินหรืองานเตรียมหนัก

**ตัวอย่างใช้งาน:** ตาราง 40 คอลัมน์ใช้ทำชาร์ตเพียง 3 คอลัมน์ การเลือก 3 คอลัมน์ล่วงหน้าอาจช่วยได้ เป็นตัวอย่างเงื่อนไข ไม่ใช่ผลทดลองใหม่

**คำเกี่ยวข้อง:** Query / SQL / Query Materialization · Pre-computation / Pre-aggregation · Data Freshness / Cache Invalidation

**อ้างอิงบริบท:** §3.2, §5 · PDF หน้า 2, 4

#### Pre-rendering / Initial Pre-rendering

**คำอ่าน:** พรีเรนเดอริง · อินิเชียล พรีเรนเดอริง

**ความหมาย:** วาดภาพก่อนช่วงเปิดเว็บ Initial pre-rendering เตรียมเฉพาะภาพสถานะเริ่มต้นแล้วเปิดการโต้ตอบภายหลัง

**ที่มาของแนวคิด:** Pre-render ไม่เหมือน precompute ผลคิวรี เพราะขั้นแรกได้ภาพพร้อมแสดง ส่วนอีกขั้นได้ข้อมูลที่ต้องนำมาวาด

**เหตุที่เกี่ยวข้อง:** ระดับสุดท้ายของการทดลองเพิ่มภาพเริ่มต้นและ hydration ไม่ได้เตรียมภาพทุกสถานะการเลือก

**ตัวอย่างใช้งาน:** ภาพเริ่มต้นของแดชบอร์ดแสดงได้ก่อนโหลดระบบคิวรีครบ แต่เปลี่ยนช่วงข้อมูลยังต้องรันตรรกะโต้ตอบ

**คำเกี่ยวข้อง:** Rendering / SVG / Raster / Canvas · Client Hydration · SSG / SSR — Static Site Generation / Server-Side Rendering

**อ้างอิงบริบท:** §3.4, §4.3, §5 · PDF หน้า 3–4

#### JavaScript Bundle / Deployed Assets

**คำอ่าน:** จาวาสคริปต์ บันเดิล · ดีพลอยด์ แอสเซตส์

**ความหมาย:** ชุดสคริปต์และไฟล์ที่ส่งไปใช้เมื่อเปิดเว็บ Assets รวมได้ทั้งข้อมูล ภาพ และผลคิวรี ไม่ได้หมายถึงภาพเพียงอย่างเดียว

**ที่มาของแนวคิด:** Bundle สื่อการจัดชุดโค้ดเพื่อใช้งาน ส่วน deployed คือพร้อมให้ระบบปลายทางโหลด

**เหตุที่เกี่ยวข้อง:** Publisher สร้าง JavaScript เพื่อเติมแคช ฐานข้อมูล และเริ่มคอมโพเนนต์โต้ตอบ

**ตัวอย่างใช้งาน:** มีภาพเริ่มต้นหนึ่งไฟล์ แต่ระบบโต้ตอบอาจต้องโหลดสคริปต์กับฐานข้อมูลเพิ่ม ขนาดภาพอย่างเดียวจึงไม่ใช่ SC

**คำเกี่ยวข้อง:** SC — Storage Cost / Deployment Footprint · Client Hydration · Mosaic / Mosaic Publisher / Coordinator

#### Bin / Aggregation Dimension / Cardinality

**คำอ่าน:** บิน · แอกกริเกชัน ไดเมนชัน · คาร์ดินาลิตี

**ความหมาย:** Bin คือช่วงหรือกลุ่มที่รวมค่า Dimension คือแกนการจัดกลุ่ม Cardinality คือจำนวนค่าที่แตกต่างกันของตัวแปร

**ที่มาของแนวคิด:** การรวมตามเวลาและสถานีมีสองมิติ ถ้าเพิ่มมิติหรือความละเอียด จำนวนผลที่ต้องเก็บอาจโตมาก

**เหตุที่เกี่ยวข้อง:** §3.3 เตือนพื้นที่ของผลรวมสำหรับหลายมุมมองอาจโตแบบผสมข้ามมิติ จึงควรจำกัดหรือเลือกเตรียมบางส่วน

**ตัวอย่างใช้งาน:** 24 ช่วงเวลา × 100 สถานีมี 2,400 กลุ่มก่อนนับมิติอื่น ตัวเลขเป็นตัวอย่างอธิบายการโตของสถานะ ไม่ใช่ขนาดแคชในงาน

#### Rendering / SVG / Raster / Canvas

**คำอ่าน:** เรนเดอริง · เอส-วี-จี · แรสเตอร์ · แคนวาส

**ความหมาย:** Rendering คือแปลงข้อมูลและข้อกำหนดเป็นภาพ SVG เก็บรูปร่างแบบเวกเตอร์ ส่วน raster เก็บภาพเป็นพิกเซล Canvas เป็นพื้นผิววาดภาพในเว็บ

**ที่มาของแนวคิด:** ภาพที่วาดเสร็จกับส่วนประกอบที่คำนวณภาพใหม่ได้มีบทบาทต่างกัน การส่งภาพอย่างเดียวไม่ทำให้ตัวกรองทำงาน

**เหตุที่เกี่ยวข้อง:** §3.4 ยกเวกเตอร์และบิตแมปเป็นรูปแบบภาพล่วงหน้า ส่วนกรณี property/gaia/taxis มีภาพ raster

**ตัวอย่างใช้งาน:** ภาพกราฟที่เปิดได้เร็วเป็นผลการเรนเดอร์ ส่วนชาร์ตที่เลือกช่วงแล้วคำนวณใหม่ได้ต้องมีตรรกะและข้อมูลเพิ่มเติม

### คำถามตรวจความเข้าใจ

**เหตุใดต้องจำลองอินพุต?**

เพราะคิวรีบางชุดสร้างเมื่อโต้ตอบ การอ่านข้อกำหนดอย่างเดียวอาจไม่กระตุ้นคิวรีเหล่านั้น

**ส่วนใดทำได้โดยไม่แก้ข้อกำหนดภาพ?**

เติม query cache และ materialized views ผ่าน Coordinator ส่วนที่เปลี่ยนแหล่งข้อมูลเตรียมต้องแก้ AST

**DuckDB กับ DuckDB-WASM รันที่เดียวกันในการทดลองหรือไม่?**

ไม่ Publisher ใช้ in-process DuckDB ช่วงเผยแพร่ ส่วนภาพทดลองใช้ DuckDB-WASM เป็นฐานข้อมูลในเบราว์เซอร์

### ลำดับอ่านภาพ

- **Figure 4 ฝั่งซ้ายบน:** เทียบความยาวรวมของแท่ง none, prep, cache และ prerender ก่อนอ่านส่วนย่อย Network, Render, Hydration, Activation

### Static ในงานนี้หมายถึงไม่มี active inputs [บทความ]

Publisher ตรวจว่ามี interactors หรือ inputs ที่ทำงานหรือไม่ ถ้าไม่มี สามารถส่งเฉพาะ pre-rendered web content โดยไม่เพิ่มตรรกะรันไทม์โต้ตอบ ลดภาระ JavaScript และข้อมูล
Static ไม่ได้แปลว่าข้อมูลไม่มีวันเปลี่ยน ภาพรายงานที่สร้างใหม่วันละครั้งยังเป็นภาพสถิตในแง่การโต้ตอบ ส่วนชาร์ตที่หน้าตาเหมือนกันแต่มี slider ต้องมีงานเปิดการโต้ตอบเพิ่ม

### วิธี hydration ที่วัดใช้เส้นทางสร้างคอมโพเนนต์มาตรฐาน [บทความ]

สำหรับภาพโต้ตอบ Publisher ส่ง initial state ที่วาดแล้วพร้อม JavaScript เอกสารระบุว่ากระบวนการ hydration ปัจจุบันสร้าง interactive components ผ่าน client-side rendering ตามปกติ
จึงยังมีงานเริ่มคอมโพเนนต์จำนวนมาก แม้ตัดงานวาดที่กั้นการเห็นภาพออกได้ §5 รายงานต้นทุน hydration ใกล้ full client-side render ข้อสรุปนี้เป็นเรื่องของวิธีที่ทดลอง ไม่ใช่ข้อพิสูจน์ว่า hydration ทุกแบบต้องแพงเท่ากัน

### Progressive hydration ยังไม่ใช่วิธีที่ทดลอง [บทความ]

§2.3 กล่าวถึง progressive hydration ในงานเว็บที่เกี่ยวข้อง ส่วน §4.3 บอกว่าวิธีที่ละเอียดขึ้นยังเป็นอนาคต และ §5 เสนอ finer-grained hydration เพื่อลดคอขวด
การทยอยเริ่มเฉพาะคอมโพเนนต์ที่จำเป็นเป็นตัวอย่างพื้นฐานให้เห็นทิศทาง แต่บทความนี้ไม่มีผลเปรียบเทียบวิธีนั้น จึงต้องกล่าวว่าเสนอให้ศึกษา ไม่ใช่ระบบที่ทำแล้วช่วยลด TTA ตามตัวเลขในสไลด์

หลักฐาน/ขอบเขต: §2.3, §4.3, §5 · PDF หน้า 2–4

### ภาพแผนที่พร้อม แต่กรอบเลือกยังไม่ทำงาน [ตัวอย่างพื้นฐาน]

สมมติส่งภาพแผนที่ความหนาแน่นที่วาดแล้ว ภาพมีรายละเอียดครบจึงผ่าน TTR แต่ยังลากกรอบเลือกไม่ได้เพราะส่วนรับเหตุการณ์และคิวรียังเริ่มไม่ครบ หลัง hydration และ activation จึงผ่าน TTA
ถ้าภาพนี้อ่านอย่างเดียว ระบบไม่ต้องเริ่มส่วนเลือก นั่นเป็นเหตุผลของการแยก Static/Interactive ไม่ใช่การเปลี่ยนรูปแบบไฟล์เพียงอย่างเดียว

ภาพเริ่มต้นพร้อมแสดง → TTR: เห็นข้อมูลครบ → เริ่มคอมโพเนนต์และอินพุต → TTA: พร้อมเลือกและกรอง

### ศัพท์ประจำสไลด์

#### Client Hydration

**คำอ่าน:** ไคลเอนต์ ไฮเดรชัน

**ความหมาย:** การเริ่มส่วนทำงานฝั่งไคลเอนต์เพื่อให้เนื้อหาที่ส่งมาแล้วรับการโต้ตอบได้

**ที่มาของแนวคิด:** Hydration เป็นอุปมาว่าเติมความสามารถทำงานให้ภาพหรือเนื้อหาที่นิ่ง ไม่ใช่แค่ดาวน์โหลดไฟล์ และไม่ใช่คำยืนยันว่าไม่ต้องวาดอะไรอีก

**เหตุที่เกี่ยวข้อง:** วิธีในงานนี้สร้างคอมโพเนนต์ผ่านกระบวนการเรนเดอร์ไคลเอนต์มาตรฐาน ต้นทุนจึงยังใกล้การเรนเดอร์เต็มชุด

**ตัวอย่างใช้งาน:** ภาพชาร์ตพร้อมแล้ว แต่ต้องเริ่ม Coordinator คอมโพเนนต์และตรรกะรับอินพุตก่อนกรองข้อมูลได้

**คำเกี่ยวข้อง:** Activation / Event / Input · Pre-rendering / Initial Pre-rendering · Progressive / Finer-Grained Hydration

**อ้างอิงบริบท:** §4.3, §5 · PDF หน้า 3–4

#### Static View / Interactive View / Component

**คำอ่าน:** สแตติก วิว · อินเทอร์แอ็กทีฟ วิว · คอมโพเนนต์

**ความหมาย:** View คือมุมมองแสดงข้อมูล Component คือส่วนประกอบที่มีหน้าที่ของระบบ Static ไม่มีอินพุตโต้ตอบที่ต้องเปิด ส่วน Interactive มี

**ที่มาของแนวคิด:** Static ในบริบทนี้หมายถึงการโต้ตอบ ไม่ได้แปลว่าข้อมูลไม่มีวันเปลี่ยน เว็บไซต์สามารถเผยแพร่ภาพสถิตฉบับใหม่ได้

**เหตุที่เกี่ยวข้อง:** Publisher ตรวจ active interactors/inputs มุมมองไม่โต้ตอบส่งเฉพาะเนื้อหาที่วาดแล้ว ส่วนโต้ตอบส่งภาพพร้อม JavaScript

**ตัวอย่างใช้งาน:** กราฟรายงานรายวันแบบอ่านอย่างเดียวต่างจากกราฟที่เลือกช่วงได้ แม้หน้าตาเริ่มต้นเหมือนกัน

**คำเกี่ยวข้อง:** Client Hydration · Rendering / SVG / Raster / Canvas · input

**อ้างอิงบริบท:** §4.3 · PDF หน้า 3

#### Activation / Event / Input

**คำอ่าน:** แอ็กทิเวชัน · อีเวนต์ · อินพุต

**ความหมาย:** Activation คือความพร้อมทำงาน Event คือเหตุการณ์ เช่น คลิกหรือเปลี่ยนค่า Input คือค่าหรือการกระทำที่ป้อนให้ระบบ

**ที่มาของแนวคิด:** การมีปุ่มในภาพกับการมีตรรกะรับปุ่มเป็นคนละเงื่อนไข ภาพปุ่มอย่างเดียวไม่ประมวลผลเหตุการณ์

**เหตุที่เกี่ยวข้อง:** Figure 4 แยกส่วน Hydration กับ Activation ส่วน TTA เป็นเวลาจากเริ่มจนพร้อมรับอินพุตทั้งหมด

**ตัวอย่างใช้งาน:** การเลื่อน slider ทำให้คิวรีเปลี่ยน ต้องเริ่มส่วนที่รับค่าและส่งคำขอให้ครบก่อน

**คำเกี่ยวข้อง:** TTA — Time-to-Activation · Client Hydration · Virtual DOM / Interaction Simulation

**อ้างอิงบริบท:** §3.1, §4.2–4.3, Figure 4 · PDF หน้า 2–4

#### Rendering / SVG / Raster / Canvas

**คำอ่าน:** เรนเดอริง · เอส-วี-จี · แรสเตอร์ · แคนวาส

**ความหมาย:** Rendering คือแปลงข้อมูลและข้อกำหนดเป็นภาพ SVG เก็บรูปร่างแบบเวกเตอร์ ส่วน raster เก็บภาพเป็นพิกเซล Canvas เป็นพื้นผิววาดภาพในเว็บ

**ที่มาของแนวคิด:** ภาพที่วาดเสร็จกับส่วนประกอบที่คำนวณภาพใหม่ได้มีบทบาทต่างกัน การส่งภาพอย่างเดียวไม่ทำให้ตัวกรองทำงาน

**เหตุที่เกี่ยวข้อง:** §3.4 ยกเวกเตอร์และบิตแมปเป็นรูปแบบภาพล่วงหน้า ส่วนกรณี property/gaia/taxis มีภาพ raster

**ตัวอย่างใช้งาน:** ภาพกราฟที่เปิดได้เร็วเป็นผลการเรนเดอร์ ส่วนชาร์ตที่เลือกช่วงแล้วคำนวณใหม่ได้ต้องมีตรรกะและข้อมูลเพิ่มเติม

**คำเกี่ยวข้อง:** Pre-rendering / Initial Pre-rendering · Client Hydration · Static View / Interactive View / Component

**อ้างอิงบริบท:** §3.4, §5 · PDF หน้า 3–4

#### TTR — Time-to-Render

**คำอ่าน:** ที-ที-อาร์ · ไทม์-ทู-เรนเดอร์

**ความหมาย:** เวลาตั้งแต่ส่งคำขอหน้าเว็บจนภาพข้อมูลปรากฏครบถ้วน

**ที่มาของแนวคิด:** Render คือสร้างผลที่มองเห็นได้ ตัวชี้วัดนี้จับจุดที่ภาพพร้อมสำหรับการอ่าน ไม่จับเพียงข้อความแรกที่ปรากฏ

**เหตุที่เกี่ยวข้อง:** ภาพล่วงหน้าลดงานที่กั้นการมองเห็น จึงลด TTR ได้มากกว่า TTA ในผลชุดรวม

**ตัวอย่างใช้งาน:** กำหนด t0 ตอนขอหน้าและ tภาพครบ แล้ว TTR = tภาพครบ − t0 ตัวอย่างนาฬิกาจำลอง 0→800 ms ไม่ใช่ค่าของ Figure 3

**คำเกี่ยวข้อง:** Rendering / SVG / Raster / Canvas · FCP — First Contentful Paint · TTA — Time-to-Activation

**อ้างอิงบริบท:** §3.1 · PDF หน้า 2

#### TTA — Time-to-Activation

**คำอ่าน:** ที-ที-เอ · ไทม์-ทู-แอ็กทิเวชัน

**ความหมาย:** เวลาจนระบบพร้อมตอบสนองอินพุต เช่น เลือกช่วง กรอง หรือซูม

**ที่มาของแนวคิด:** Activation คือทำให้ระบบพร้อมใช้งาน เวลานี้ไม่เท่ากับเวลาประมวลผลทุกการคลิกหลังเปิดเว็บแล้ว

**เหตุที่เกี่ยวข้อง:** แคชช่วยลดงานก่อนพร้อมโต้ตอบ แต่ภาพล่วงหน้ายังต้อง hydration จึงช่วย TTA เพิ่มเพียงเล็กน้อย

**ตัวอย่างใช้งาน:** ถ้าภาพครบที่ 800 ms แต่ตัวกรองพร้อมที่ 1,400 ms ค่า TTR กับ TTA ต่างกัน ตัวเลขเป็นตัวอย่างสอนนิยาม

**คำเกี่ยวข้อง:** TTR — Time-to-Render · TTI — Time to Interactive · Client Hydration · Activation / Event / Input

**อ้างอิงบริบท:** §3.1, §5 · PDF หน้า 2, 4

#### Progressive / Finer-Grained Hydration

**คำอ่าน:** โพรเกรสซิฟ · ไฟเนอร์-เกรนด์ ไฮเดรชัน

**ความหมาย:** Progressive สื่อการทยอยเปิดส่วนทำงาน ส่วน finer-grained สื่อการจัดการระดับย่อยกว่าการเริ่มทั้งชุด

**ที่มาของแนวคิด:** Granularity คือระดับความละเอียดของหน่วยงาน แนวคิดต่างกันแต่เกี่ยวข้องกับการลดงานเริ่มต้นที่ไม่จำเป็น

**เหตุที่เกี่ยวข้อง:** Progressive อยู่ใน Related Work §2.3 ส่วนวิธีละเอียดขึ้นเป็นข้อเสนอใน §5 ไม่ใช่วิธีที่ทดลองแล้ว

**ตัวอย่างใช้งาน:** อาจเริ่มตัวกรองสำคัญก่อนส่วนที่ยังไม่ใช้งาน เป็นตัวอย่างพื้นฐาน ไม่ใช่ขั้นตอนที่ยืนยันว่า Publisher รุ่นทดลองทำได้

**คำเกี่ยวข้อง:** Client Hydration · Hybrid Publish/Runtime Strategies · Activation / Event / Input

**อ้างอิงบริบท:** §2.3, §4.3, §5 · PDF หน้า 2–4

#### Pre-rendering / Initial Pre-rendering

**คำอ่าน:** พรีเรนเดอริง · อินิเชียล พรีเรนเดอริง

**ความหมาย:** วาดภาพก่อนช่วงเปิดเว็บ Initial pre-rendering เตรียมเฉพาะภาพสถานะเริ่มต้นแล้วเปิดการโต้ตอบภายหลัง

**ที่มาของแนวคิด:** Pre-render ไม่เหมือน precompute ผลคิวรี เพราะขั้นแรกได้ภาพพร้อมแสดง ส่วนอีกขั้นได้ข้อมูลที่ต้องนำมาวาด

**เหตุที่เกี่ยวข้อง:** ระดับสุดท้ายของการทดลองเพิ่มภาพเริ่มต้นและ hydration ไม่ได้เตรียมภาพทุกสถานะการเลือก

**ตัวอย่างใช้งาน:** ภาพเริ่มต้นของแดชบอร์ดแสดงได้ก่อนโหลดระบบคิวรีครบ แต่เปลี่ยนช่วงข้อมูลยังต้องรันตรรกะโต้ตอบ

**คำเกี่ยวข้อง:** Rendering / SVG / Raster / Canvas · Client Hydration · SSG / SSR — Static Site Generation / Server-Side Rendering

**อ้างอิงบริบท:** §3.4, §4.3, §5 · PDF หน้า 3–4

#### JavaScript Bundle / Deployed Assets

**คำอ่าน:** จาวาสคริปต์ บันเดิล · ดีพลอยด์ แอสเซตส์

**ความหมาย:** ชุดสคริปต์และไฟล์ที่ส่งไปใช้เมื่อเปิดเว็บ Assets รวมได้ทั้งข้อมูล ภาพ และผลคิวรี ไม่ได้หมายถึงภาพเพียงอย่างเดียว

**ที่มาของแนวคิด:** Bundle สื่อการจัดชุดโค้ดเพื่อใช้งาน ส่วน deployed คือพร้อมให้ระบบปลายทางโหลด

**เหตุที่เกี่ยวข้อง:** Publisher สร้าง JavaScript เพื่อเติมแคช ฐานข้อมูล และเริ่มคอมโพเนนต์โต้ตอบ

**ตัวอย่างใช้งาน:** มีภาพเริ่มต้นหนึ่งไฟล์ แต่ระบบโต้ตอบอาจต้องโหลดสคริปต์กับฐานข้อมูลเพิ่ม ขนาดภาพอย่างเดียวจึงไม่ใช่ SC

**คำเกี่ยวข้อง:** SC — Storage Cost / Deployment Footprint · Client Hydration · Mosaic / Mosaic Publisher / Coordinator

**อ้างอิงบริบท:** §4.2–4.3 · PDF หน้า 3

#### Network Transfer / Local Server / WAN

**คำอ่าน:** เน็ตเวิร์ก ทรานส์เฟอร์ · โลคัล เซิร์ฟเวอร์ · แวน

**ความหมาย:** Network transfer คือการส่งทรัพยากรระหว่างระบบ Local server คือเซิร์ฟเวอร์ใกล้สภาพแวดล้อมทดลอง WAN คือเครือข่ายบริเวณกว้าง

**ที่มาของแนวคิด:** เวลาคำนวณกับเวลารับส่งเป็นคนละต้นทุน การเพิ่มไฟล์ล่วงหน้าอาจลดคำนวณแต่เพิ่มข้อมูลที่ต้องส่ง

**เหตุที่เกี่ยวข้อง:** Figure 4 แยกส่วน Network ผลทดลองผ่าน local server จึงไม่รับรองผลบนเครือข่ายมือถือหรือ WAN

**ตัวอย่างใช้งาน:** ชุดแคชใหญ่ที่โหลดเร็วบนเครื่องทดลองอาจโหลดช้าบนเครือข่ายจำกัด ต้องวัดใหม่ ไม่ใช้ SC แทนปริมาณส่งทุกเซสชันโดยตรง

**คำเกี่ยวข้อง:** SC — Storage Cost / Deployment Footprint · Latency / Perceived Latency / Interface Lag · CDN / Edge / IoT Sensor Dashboard

**อ้างอิงบริบท:** Figure 4, §5 · PDF หน้า 4; WAN เป็นพื้นฐานประกอบ

#### Δ / Percentage Change / Percentage Point

**คำอ่าน:** เดลตา · เพอร์เซ็นเทจ เชนจ์ · เพอร์เซ็นเทจ พอยต์

**ความหมาย:** Δ หมายถึงการเปลี่ยนแปลง Percentage change ใช้เทียบค่ากับฐาน ส่วนจุดเปอร์เซ็นต์ใช้ลบอัตราที่ใช้ฐานเดียวกัน

**ที่มาของแนวคิด:** การลบ 33.3% กับ 32.3% ได้ 1.0 จุดเปอร์เซ็นต์ ถ้าจะบอกอัตราเร็วขึ้นจากระดับแคชโดยตรงต้องคำนวณจากเวลาเหลือ

**เหตุที่เกี่ยวข้อง:** ผลเพิ่ม TTA ระหว่าง +cache กับ +most เป็น 1.0 จุดเปอร์เซ็นต์ของการลดเทียบ none ไม่ใช่ 1% ของเวลาแคช

**ตัวอย่างใช้งาน:** ฐานสมมติ 1,000 ms เหลือ 677 ms กับ 667 ms ต่าง 10 ms หรือราว 1.48% ของ 677 ms ตัวอย่างอนุมานจากอัตราเฉลี่ย ไม่ใช่ผลรายกรณี

**คำเกี่ยวข้อง:** Baseline / none / +prep / +cache / +most · TTA — Time-to-Activation · Mean / Average / ms / k / M / RAM / Node.js

**อ้างอิงบริบท:** คำนวณจาก Table 1 · PDF หน้า 4

#### SSG / SSR — Static Site Generation / Server-Side Rendering

**คำอ่าน:** เอส-เอส-จี · เอส-เอส-อาร์

**ความหมาย:** SSG สร้างหน้าไว้ก่อนช่วงขอใช้งาน ส่วน SSR ในคำอธิบาย §2.3 สร้างเนื้อหาฝั่งเซิร์ฟเวอร์ตามคำขอ ทั้งคู่อาจมีการเปิดตรรกะไคลเอนต์ตามมา

**ที่มาของแนวคิด:** ชื่อคล้ายกันเพราะสร้างเนื้อหาก่อนเบราว์เซอร์วาดเอง แต่เวลาที่เกิดงานต่างกัน ห้ามรวมว่า SSR ทุกแบบทำตอน build

**เหตุที่เกี่ยวข้อง:** เป็นแนวคิดเว็บที่ผู้วิจัยนำมาเชื่อมกับภาพข้อมูล งานนี้ศึกษาช่วงเผยแพร่โดยเฉพาะ

**ตัวอย่างใช้งาน:** เว็บบทความสถิตเตรียม HTML ไว้ได้ ส่วนเว็บตามคำขออาจสร้างบนเซิร์ฟเวอร์ ทั้งสองไม่ทำให้ข้อมูลทุกสถานะของชาร์ตพร้อมโดยอัตโนมัติ

**คำเกี่ยวข้อง:** Publish-Time Optimization · Pre-rendering / Initial Pre-rendering · Client Hydration

- อย่าลบ TTR ออกจาก TTA แล้วเรียกผลต่างทั้งหมดว่า Hydration โดยไม่มี breakdown

### คำถามตรวจความเข้าใจ

**เหตุใดลด TTR มากกว่า TTA ได้?**

ภาพล่วงหน้าทำให้มองเห็นก่อน แต่ระบบโต้ตอบยังต้องเริ่มคอมโพเนนต์ วิธี hydration ที่ทดลองยังมีต้นทุนสูง

**Static View ต้องมีข้อมูลสดตลอดหรือไม่?**

คำ static ในการแยกนี้หมายถึงไม่มีอินพุตโต้ตอบ ไม่ได้กำหนดว่าข้อมูลต้นทางจะเปลี่ยนได้หรือไม่ได้

**งานอนาคตที่แก้คอขวดนี้คืออะไร?**

§5 เสนอศึกษาการ hydration ที่ละเอียดขึ้นหรือวิธีลดภาระเริ่มระบบ ยังไม่มีผล benchmark ของวิธีใหม่ในงานนี้

- **กราฟซ้าย: ห้าคอลัมน์:** Airlines, Property, Flights, Gaia, Taxis คือคนละข้อกำหนดภาพ แกนนอนแต่ละช่องคือจำนวนแถว 10k–10M ไม่ใช่เวลา

#### TTR — Time-to-Render

**คำอ่าน:** ที-ที-อาร์ · ไทม์-ทู-เรนเดอร์

**ความหมาย:** เวลาตั้งแต่ส่งคำขอหน้าเว็บจนภาพข้อมูลปรากฏครบถ้วน

**ที่มาของแนวคิด:** Render คือสร้างผลที่มองเห็นได้ ตัวชี้วัดนี้จับจุดที่ภาพพร้อมสำหรับการอ่าน ไม่จับเพียงข้อความแรกที่ปรากฏ

**เหตุที่เกี่ยวข้อง:** ภาพล่วงหน้าลดงานที่กั้นการมองเห็น จึงลด TTR ได้มากกว่า TTA ในผลชุดรวม

**ตัวอย่างใช้งาน:** กำหนด t0 ตอนขอหน้าและ tภาพครบ แล้ว TTR = tภาพครบ − t0 ตัวอย่างนาฬิกาจำลอง 0→800 ms ไม่ใช่ค่าของ Figure 3

**คำเกี่ยวข้อง:** Rendering / SVG / Raster / Canvas · FCP — First Contentful Paint · TTA — Time-to-Activation

#### TTA — Time-to-Activation

**คำอ่าน:** ที-ที-เอ · ไทม์-ทู-แอ็กทิเวชัน

**ความหมาย:** เวลาจนระบบพร้อมตอบสนองอินพุต เช่น เลือกช่วง กรอง หรือซูม

**ที่มาของแนวคิด:** Activation คือทำให้ระบบพร้อมใช้งาน เวลานี้ไม่เท่ากับเวลาประมวลผลทุกการคลิกหลังเปิดเว็บแล้ว

**เหตุที่เกี่ยวข้อง:** แคชช่วยลดงานก่อนพร้อมโต้ตอบ แต่ภาพล่วงหน้ายังต้อง hydration จึงช่วย TTA เพิ่มเพียงเล็กน้อย

**ตัวอย่างใช้งาน:** ถ้าภาพครบที่ 800 ms แต่ตัวกรองพร้อมที่ 1,400 ms ค่า TTR กับ TTA ต่างกัน ตัวเลขเป็นตัวอย่างสอนนิยาม

**คำเกี่ยวข้อง:** TTR — Time-to-Render · TTI — Time to Interactive · Client Hydration · Activation / Event / Input

**ที่มาของแนวคิด:** Cost ในชื่อหมายถึงต้นทุนด้านพื้นที่ ไม่ได้รายงานเป็นค่าใช้จ่ายเงิน Footprint คือขนาดรวมที่ต้องเก็บไว้เพื่อเผยแพร่

**ตัวอย่างใช้งาน:** ถ้าชุดเดิม 100 MB และเพิ่ม 21.2% ขนาดใหม่คือ 121.2 MB เป็นตัวอย่างคำนวณ ไม่ใช่ขนาดจริงที่บทความรายงาน

#### Network Transfer / Local Server / WAN

**คำอ่าน:** เน็ตเวิร์ก ทรานส์เฟอร์ · โลคัล เซิร์ฟเวอร์ · แวน

**ความหมาย:** Network transfer คือการส่งทรัพยากรระหว่างระบบ Local server คือเซิร์ฟเวอร์ใกล้สภาพแวดล้อมทดลอง WAN คือเครือข่ายบริเวณกว้าง

**ที่มาของแนวคิด:** เวลาคำนวณกับเวลารับส่งเป็นคนละต้นทุน การเพิ่มไฟล์ล่วงหน้าอาจลดคำนวณแต่เพิ่มข้อมูลที่ต้องส่ง

**ตัวอย่างใช้งาน:** ชุดแคชใหญ่ที่โหลดเร็วบนเครื่องทดลองอาจโหลดช้าบนเครือข่ายจำกัด ต้องวัดใหม่ ไม่ใช้ SC แทนปริมาณส่งทุกเซสชันโดยตรง

**คำอ่าน:** เทรด-ออฟ · เบนช์มาร์ก · เธรตส์ ทู วะลิดิที

**ความหมาย:** Trade-off คือได้ประโยชน์ด้านหนึ่งโดยมีต้นทุนอีกด้าน Benchmark คือการทดสอบเทียบภายใต้เงื่อนไขกำหนด Threats to validity คือปัจจัยที่จำกัดความน่าเชื่อถือหรือการขยายข้อสรุป

**ที่มาของแนวคิด:** ผลวัดตอบคำถามภายในขอบเขตทดลอง การวิจารณ์ต้องแยกระหว่างผลไม่ดีจริงกับข้อมูลที่ยังไม่เพียงพอ

**เหตุที่เกี่ยวข้อง:** พื้นที่และ hydration เป็นต้นทุนที่มีหลักฐาน ส่วนมือถือ WAN และข้อมูลสดยังไม่ถูกทดสอบใน PDF

**ความหมาย:** เตรียมข้อมูลโดยเลือกคอลัมน์ที่ใช้ แปลงค่า หรือจัดรูปข้อมูลก่อนนำไปแสดง

#### Query Result Cache / Cache

**คำอ่าน:** คิวรี รีซัลต์ แคช · แคช

**ความหมาย:** ที่เก็บผลคิวรีซึ่งเคยคำนวณแล้ว เพื่อใช้ซ้ำเมื่อมีคำขอที่ตรงกัน

**ที่มาของแนวคิด:** Cache เน้นการนำผลเดิมกลับมาใช้ ลดงานคำนวณ ไม่ใช่ชื่อรูปแบบไฟล์หรือฐานข้อมูลชนิดหนึ่ง

**เหตุที่เกี่ยวข้อง:** Publisher เตรียม result cache แล้วเติมให้ Coordinator ตอนเริ่มระบบ ต่างจากรอสร้างระหว่างใช้งาน

**ตัวอย่างใช้งาน:** ผลยอดรวมตามเดือนที่เตรียมไว้ตอบคิวรีเดิมได้ แต่เมื่อข้อมูลเปลี่ยนต้องจัดการความถูกต้องของผลเก่า

**คำเกี่ยวข้อง:** Pre-computation / Pre-aggregation · Pre-aggregated Materialized View · Data Freshness / Cache Invalidation

#### Pre-rendering / Initial Pre-rendering

**คำอ่าน:** พรีเรนเดอริง · อินิเชียล พรีเรนเดอริง

**ความหมาย:** วาดภาพก่อนช่วงเปิดเว็บ Initial pre-rendering เตรียมเฉพาะภาพสถานะเริ่มต้นแล้วเปิดการโต้ตอบภายหลัง

**ที่มาของแนวคิด:** Pre-render ไม่เหมือน precompute ผลคิวรี เพราะขั้นแรกได้ภาพพร้อมแสดง ส่วนอีกขั้นได้ข้อมูลที่ต้องนำมาวาด

**เหตุที่เกี่ยวข้อง:** ระดับสุดท้ายของการทดลองเพิ่มภาพเริ่มต้นและ hydration ไม่ได้เตรียมภาพทุกสถานะการเลือก

**ตัวอย่างใช้งาน:** ภาพเริ่มต้นของแดชบอร์ดแสดงได้ก่อนโหลดระบบคิวรีครบ แต่เปลี่ยนช่วงข้อมูลยังต้องรันตรรกะโต้ตอบ

#### Bin / Aggregation Dimension / Cardinality

**คำอ่าน:** บิน · แอกกริเกชัน ไดเมนชัน · คาร์ดินาลิตี

**ความหมาย:** Bin คือช่วงหรือกลุ่มที่รวมค่า Dimension คือแกนการจัดกลุ่ม Cardinality คือจำนวนค่าที่แตกต่างกันของตัวแปร

### คำถามตรวจความเข้าใจ

**กราฟกับตารางใช้สถิติเดียวกันหรือไม่?**

ไม่ Figure 3 ใช้ median และ IQR ของเวลา ms; Table 1 ใช้ mean ± σ ของการเปลี่ยนแปลงร้อยละเทียบ none

**+most กับ +prerender ต่างระดับกันหรือไม่?**

ไม่ ในงานนี้เป็นชื่อที่ใช้กับระดับรวมสุดท้าย ต่างตำแหน่งในตารางกับกราฟ/เนื้อหา

**เหตุใด +prep แทบไม่ช่วย?**

ชุดทดลองไม่มีคอลัมน์เกินหรืองานเตรียมซับซ้อน จึงไม่มีงานมากให้ย้าย ไม่ได้หักล้างประโยชน์กับชุดข้อมูลที่เตรียมหนัก

**SC สูงขึ้นหมายถึง network latency สูงขึ้นเท่ากันเสมอหรือไม่?**

ไม่ SC เป็นขนาดทรัพยากรเผยแพร่ ส่วนเวลาส่งขึ้นกับสิ่งที่โหลดและสภาพแวดล้อม ใน local server ของงานนี้ผลเครือข่ายต่างกันน้อย

- **ขวาบน: ขอบเขตเครื่องและเครือข่าย:** ระบุว่า local server กับ M1 Pro ยังไม่ครอบคลุมมือถือหรือ WAN โดยไม่กล่าวว่าผลบนระบบเหล่านั้นล้มเหลว

### ทิศทางแรก: ลดภาระ hydration ให้ตรงงานจำเป็น [บทความ]

§5 เสนอ finer-grained hydration หรือวิธีลด overhead เพราะวิธีปัจจุบันยังสร้างคอมโพเนนต์ผ่านเส้นทางเรนเดอร์มาตรฐาน หากลดงานเริ่มต้นได้อาจช่วย TTA ที่ยังค้าง
ตัวอย่างพื้นฐานคือแบ่งหน่วยที่เริ่มให้เล็กลงหรือทยอยเปิดบางส่วน แต่ PDF ไม่ระบุอัลกอริทึมสุดท้ายและไม่ได้ทดลองผล จึงไม่ควรให้ตัวเลขความเร็วของแนวทางใหม่นี้

หลักฐาน/ขอบเขต: §4.3, §5 · PDF หน้า 3–4

### ทิศทางที่สองส่วนแรก: Hybrid [บทความเชื่อมตัวอย่าง]

§6 เสนอ hybrid publish/runtime แก้ความตึงระหว่างงานที่คาดได้ก่อนกับงานใหม่ตอนใช้งาน ไม่จำเป็นต้องเลือกระหว่างเตรียมทั้งหมดกับรันสดทั้งหมดเพียงสองทาง
ตัวอย่างต่อยอดคือเตรียมผลรวมประวัติที่เสถียร ส่วนข้อมูลล่าสุดหรือเงื่อนไขที่ไม่เคยเตรียมยังรันสดได้ แต่ต้องออกแบบความสอดคล้องของสองส่วนและวัดใหม่ ตัวอย่างนี้ไม่ได้เป็น implementation ที่รายงานผลแล้ว

หลักฐาน/ขอบเขต: §6 · PDF หน้า 4; ตัวอย่างเป็นข้ออนุมาน

### ทิศทางที่สองส่วนหลัง: Incremental Regeneration [บทความเชื่อมตัวอย่าง]

Incremental regeneration สร้างใหม่เฉพาะส่วนที่ข้อมูลเปลี่ยน จึงอาจลดเวลาทำงานซ้ำรอบเผยแพร่ ต่างจาก hybrid ที่แบ่งงานระหว่างสองช่วง แม้ใช้ร่วมกันได้
ตัวอย่างตารางแบ่งรายวัน: วันใหม่อาจทำให้ปรับพาร์ทิชันหนึ่งส่วน แต่ผลรวมข้ามวันหรือภาพที่พึ่งพาส่วนนั้นต้องปรับด้วย การรู้ dependency จึงสำคัญ PDF ระบุเป็นทิศทาง ไม่ได้ให้วิธีติดตาม dependency ที่พิสูจน์แล้ว

หลักฐาน/ขอบเขต: §6 · PDF หน้า 4; รายละเอียดตัวอย่างเป็นพื้นฐาน

### ทิศทางที่สาม: เลือกการตั้งค่าตามต้นทุนจริง [บทความ]

§6 เสนอ automatic selection จาก input data และ visualization specifications เพราะข้อมูลเล็กอาจไม่คุ้มโหลดผลล่วงหน้า ข้อมูลใหญ่หรือคิวรีหนักอาจได้ประโยชน์ และหลายมิติอาจเพิ่มพื้นที่มาก
การเลือกอัตโนมัติไม่เท่ากับต้องใช้ LLM หรือ AI PDF ไม่ระบุวิธีชนิดนั้น สิ่งที่เสนอคือค้นการตั้งค่าที่มีประสิทธิผลตามข้อมูลกับข้อกำหนด ไม่ใช่เปิดทุกกลยุทธ์ตลอด

หลักฐาน/ขอบเขต: §4.2, §5–6 · PDF หน้า 3–4

### ประโยคจบที่อิงผลและยังรักษาขอบเขต [การวิเคราะห์]

ข้อค้นพบคือการย้ายงานไปก่อนเซสชันช่วยลดเวลาเริ่มภาพและเริ่มโต้ตอบในชุดทดสอบ แต่ต้องประเมินพื้นที่ hydration และการสร้างผลใหม่ด้วย เป็นข้อสรุประบบที่อธิบายได้จากหลักฐาน
ไม่ควรปิดท้ายด้วยคำรับรองว่าเป็นคำตอบสำหรับทุกเว็บ หรือแนะนำให้เปิดทุกระดับเสมอ งานนี้เน้นข้อมูลเสถียรและการโต้ตอบคาดได้ ส่วนแนวทางใหม่ยังต้องวิจัยต่อ

หลักฐาน/ขอบเขต: §5–6 · PDF หน้า 4

### สามแนวทางแก้คนละปัญหา [ตัวอย่างต่อยอด]

Hydration ละเอียดขึ้นแก้งานเริ่มไคลเอนต์ Hybrid จัดงานที่เตรียมได้กับงานที่ต้องสด Incremental ลดงานสร้างทรัพยากรใหม่ ส่วน automatic configuration ช่วยเลือกว่าจะใช้วิธีใดตามเงื่อนไข
หัวข้อขวาในสไลด์มีสามรายการเพราะ Hybrid กับ Incremental อยู่ในรายการเดียวกัน แต่สองคำมีความหมายต่างกัน การตอบกรรมการต้องแยกได้ ไม่ใช่ท่องชื่อรวมกัน

Hydration: ลดงานเริ่มต้น → Hybrid: แบ่งช่วงคำนวณ → Incremental: สร้างใหม่เฉพาะส่วน → Automatic: เลือกตามเงื่อนไข

#### Query Result Cache / Cache

**คำอ่าน:** คิวรี รีซัลต์ แคช · แคช

**ความหมาย:** ที่เก็บผลคิวรีซึ่งเคยคำนวณแล้ว เพื่อใช้ซ้ำเมื่อมีคำขอที่ตรงกัน

**ที่มาของแนวคิด:** Cache เน้นการนำผลเดิมกลับมาใช้ ลดงานคำนวณ ไม่ใช่ชื่อรูปแบบไฟล์หรือฐานข้อมูลชนิดหนึ่ง

**เหตุที่เกี่ยวข้อง:** Publisher เตรียม result cache แล้วเติมให้ Coordinator ตอนเริ่มระบบ ต่างจากรอสร้างระหว่างใช้งาน

**ตัวอย่างใช้งาน:** ผลยอดรวมตามเดือนที่เตรียมไว้ตอบคิวรีเดิมได้ แต่เมื่อข้อมูลเปลี่ยนต้องจัดการความถูกต้องของผลเก่า

**อ้างอิงบริบท:** §3.3, §4.3 · PDF หน้า 2–3

#### TTR — Time-to-Render

**คำอ่าน:** ที-ที-อาร์ · ไทม์-ทู-เรนเดอร์

**ความหมาย:** เวลาตั้งแต่ส่งคำขอหน้าเว็บจนภาพข้อมูลปรากฏครบถ้วน

**ที่มาของแนวคิด:** Render คือสร้างผลที่มองเห็นได้ ตัวชี้วัดนี้จับจุดที่ภาพพร้อมสำหรับการอ่าน ไม่จับเพียงข้อความแรกที่ปรากฏ

**เหตุที่เกี่ยวข้อง:** ภาพล่วงหน้าลดงานที่กั้นการมองเห็น จึงลด TTR ได้มากกว่า TTA ในผลชุดรวม

**ตัวอย่างใช้งาน:** กำหนด t0 ตอนขอหน้าและ tภาพครบ แล้ว TTR = tภาพครบ − t0 ตัวอย่างนาฬิกาจำลอง 0→800 ms ไม่ใช่ค่าของ Figure 3

**คำเกี่ยวข้อง:** Rendering / SVG / Raster / Canvas · FCP — First Contentful Paint · TTA — Time-to-Activation

**คำอ่าน:** ที-ที-เอ · ไทม์-ทู-แอ็กทิเวชัน

**ความหมาย:** เวลาจนระบบพร้อมตอบสนองอินพุต เช่น เลือกช่วง กรอง หรือซูม

**ที่มาของแนวคิด:** Activation คือทำให้ระบบพร้อมใช้งาน เวลานี้ไม่เท่ากับเวลาประมวลผลทุกการคลิกหลังเปิดเว็บแล้ว

**เหตุที่เกี่ยวข้อง:** แคชช่วยลดงานก่อนพร้อมโต้ตอบ แต่ภาพล่วงหน้ายังต้อง hydration จึงช่วย TTA เพิ่มเพียงเล็กน้อย

**ตัวอย่างใช้งาน:** ถ้าภาพครบที่ 800 ms แต่ตัวกรองพร้อมที่ 1,400 ms ค่า TTR กับ TTA ต่างกัน ตัวเลขเป็นตัวอย่างสอนนิยาม

**คำเกี่ยวข้อง:** TTR — Time-to-Render · TTI — Time to Interactive · Client Hydration · Activation / Event / Input

**อ้างอิงบริบท:** §3.1, §5 · PDF หน้า 2, 4

#### SC — Storage Cost / Deployment Footprint

**คำอ่าน:** เอส-ซี · สตอเรจ คอสต์ · ดีพลอยเมนต์ ฟุตพรินต์

**ความหมาย:** ขนาดทรัพยากรทั้งหมดที่เผยแพร่ เช่น ข้อมูล สคริปต์ ภาพ และผลคำนวณล่วงหน้า

**ที่มาของแนวคิด:** Cost ในชื่อหมายถึงต้นทุนด้านพื้นที่ ไม่ได้รายงานเป็นค่าใช้จ่ายเงิน Footprint คือขนาดรวมที่ต้องเก็บไว้เพื่อเผยแพร่

**เหตุที่เกี่ยวข้อง:** บทความเปรียบเทียบการเปลี่ยนแปลง SC กับ none เพื่อเห็นต้นทุนของการเร่งความเร็ว

**ตัวอย่างใช้งาน:** ถ้าชุดเดิม 100 MB และเพิ่ม 21.2% ขนาดใหม่คือ 121.2 MB เป็นตัวอย่างคำนวณ ไม่ใช่ขนาดจริงที่บทความรายงาน

**คำเกี่ยวข้อง:** Trade-off / Benchmark / Threats to Validity · Network Transfer / Local Server / WAN · Pre-computation / Pre-aggregation

**อ้างอิงบริบท:** §1, §3.1, Table 1 · PDF หน้า 1–2, 4

#### Client Hydration

**คำอ่าน:** ไคลเอนต์ ไฮเดรชัน

**ความหมาย:** การเริ่มส่วนทำงานฝั่งไคลเอนต์เพื่อให้เนื้อหาที่ส่งมาแล้วรับการโต้ตอบได้

**ที่มาของแนวคิด:** Hydration เป็นอุปมาว่าเติมความสามารถทำงานให้ภาพหรือเนื้อหาที่นิ่ง ไม่ใช่แค่ดาวน์โหลดไฟล์ และไม่ใช่คำยืนยันว่าไม่ต้องวาดอะไรอีก

**เหตุที่เกี่ยวข้อง:** วิธีในงานนี้สร้างคอมโพเนนต์ผ่านกระบวนการเรนเดอร์ไคลเอนต์มาตรฐาน ต้นทุนจึงยังใกล้การเรนเดอร์เต็มชุด

**ตัวอย่างใช้งาน:** ภาพชาร์ตพร้อมแล้ว แต่ต้องเริ่ม Coordinator คอมโพเนนต์และตรรกะรับอินพุตก่อนกรองข้อมูลได้

**คำเกี่ยวข้อง:** Activation / Event / Input · Pre-rendering / Initial Pre-rendering · Progressive / Finer-Grained Hydration

**อ้างอิงบริบท:** §4.3, §5 · PDF หน้า 3–4

#### Progressive / Finer-Grained Hydration

**คำอ่าน:** โพรเกรสซิฟ · ไฟเนอร์-เกรนด์ ไฮเดรชัน

**ความหมาย:** Progressive สื่อการทยอยเปิดส่วนทำงาน ส่วน finer-grained สื่อการจัดการระดับย่อยกว่าการเริ่มทั้งชุด

**ที่มาของแนวคิด:** Granularity คือระดับความละเอียดของหน่วยงาน แนวคิดต่างกันแต่เกี่ยวข้องกับการลดงานเริ่มต้นที่ไม่จำเป็น

**เหตุที่เกี่ยวข้อง:** Progressive อยู่ใน Related Work §2.3 ส่วนวิธีละเอียดขึ้นเป็นข้อเสนอใน §5 ไม่ใช่วิธีที่ทดลองแล้ว

**ตัวอย่างใช้งาน:** อาจเริ่มตัวกรองสำคัญก่อนส่วนที่ยังไม่ใช้งาน เป็นตัวอย่างพื้นฐาน ไม่ใช่ขั้นตอนที่ยืนยันว่า Publisher รุ่นทดลองทำได้

**คำเกี่ยวข้อง:** Client Hydration · Hybrid Publish/Runtime Strategies · Activation / Event / Input

**อ้างอิงบริบท:** §2.3, §4.3, §5 · PDF หน้า 2–4

#### Hybrid Publish/Runtime Strategies

**คำอ่าน:** ไฮบริด พับลิช รันไทม์ สแตรทิจีส์

**ความหมาย:** ผสานส่วนที่คำนวณล่วงหน้าได้กับส่วนที่คำนวณตอนใช้งาน

**ที่มาของแนวคิด:** Hybrid หมายถึงใช้หลายแนวทางร่วมกัน งานที่เสถียรเหมาะเตรียมไว้ ส่วนคำถามใหม่หรือข้อมูลสดอาจทำตอนรันไทม์

**เหตุที่เกี่ยวข้อง:** ทีมวิจัยระบุเป็นแนวทางอนาคตใน §6 ไม่ได้รายงาน benchmark ของวิธี hybrid ที่พัฒนาใหม่

**ตัวอย่างใช้งาน:** เก็บผลรวมประวัติไว้ แล้วคำนวณข้อมูลช่วงล่าสุดเพิ่ม เป็นตัวอย่างสถาปัตยกรรมต่อยอด ต้องทดสอบความถูกต้องและความเร็ว

**คำเกี่ยวข้อง:** Publish-Time Optimization · Run-Time / Runtime · Incremental Regeneration

**อ้างอิงบริบท:** §6 · PDF หน้า 4

#### Incremental Regeneration

**คำอ่าน:** อินครีเมนทัล รีเจเนอเรชัน

**ความหมาย:** สร้างทรัพยากรใหม่เฉพาะส่วนที่ได้รับผลจากการเปลี่ยนข้อมูล แทนสร้างทั้งหมดใหม่

**ที่มาของแนวคิด:** Incremental เน้นเพิ่มหรือปรับทีละส่วน Regeneration คือสร้างผลใหม่ ต้องทราบความสัมพันธ์ระหว่างข้อมูลกับผลที่เก็บ

**เหตุที่เกี่ยวข้อง:** เป็นแนวทางอนาคตของผู้วิจัย ไม่ได้มีอัลกอริทึมและผลวัดเพิ่มเติมในบทความนี้

**ตัวอย่างใช้งาน:** ข้อมูลวันใหม่อาจทำให้ปรับพาร์ทิชันวันนั้นได้ แต่ผลรวมข้ามวันอาจต้องแก้ด้วย ไม่ควรถือว่าแก้ไฟล์เดียวแล้วถูกทั้งหมดเสมอ

**คำเกี่ยวข้อง:** Data Freshness / Cache Invalidation · Hybrid Publish/Runtime Strategies · Pre-aggregated Materialized View

**อ้างอิงบริบท:** §6 · PDF หน้า 4

#### Automatic Optimization Configuration

**คำอ่าน:** ออโตแมติก ออปทิไมเซชัน คอนฟิกกิวเรชัน

**ความหมาย:** เลือกระดับการปรับปรุงตามข้อมูลและข้อกำหนดภาพโดยอัตโนมัติ

**ที่มาของแนวคิด:** Configuration คือชุดการตั้งค่า การเลือกที่ดีต้องชั่งเวลา พื้นที่ จำนวนสถานะ และความสด ไม่จำเป็นต้องใช้ AI

**เหตุที่เกี่ยวข้อง:** ผู้วิจัยเสนอเป็นงานอนาคต ปัจจุบัน Publisher ใช้ระดับที่เลือกไว้แล้ว

**ตัวอย่างใช้งาน:** ระบบอาจประเมินว่าข้อมูลเล็กไม่ต้องโหลดแคชใหญ่ ส่วนข้อมูลหนักใช้ผลรวม ตัวอย่างเกณฑ์นี้ไม่ใช่อัลกอริทึมที่ยืนยันใน PDF

**คำเกี่ยวข้อง:** Trade-off / Benchmark / Threats to Validity · Baseline / none / +prep / +cache / +most · Data Freshness / Cache Invalidation

**อ้างอิงบริบท:** §4.2, §6 · PDF หน้า 3–4

#### Data Freshness / Cache Invalidation

**คำอ่าน:** เดตา เฟรชเนส · แคช อินวาลิเดชัน

**ความหมาย:** Freshness คือความทันสมัยของผลเทียบกับข้อมูลต้นทาง Invalidation คือทำให้ผลเก่าไม่ถูกใช้ต่อเมื่อไม่ตรงข้อมูลแล้ว

**ที่มาของแนวคิด:** การใช้ผลซ้ำต้องตรวจว่าเงื่อนไขเดิมยังจริง มิฉะนั้นเร็วแต่เป็นข้อมูลเก่า การสร้างทรัพยากรใหม่มีเวลาและต้นทุน

**เหตุที่เกี่ยวข้อง:** §3.2 พิจารณาข้อมูลที่เปลี่ยนและการสร้างใหม่ §6 เสนอ incremental regeneration

**ตัวอย่างใช้งาน:** ภาพและผลรวมควรอิงข้อมูลรุ่นเดียวกัน การจัดรุ่นและตรวจความสอดคล้องเป็นตัวอย่างออกแบบเพิ่ม ไม่ใช่กลไกที่ประเมินในงาน

**คำเกี่ยวข้อง:** Incremental Regeneration · Query Result Cache / Cache · Hybrid Publish/Runtime Strategies

**อ้างอิงบริบท:** §3.2, §6 · PDF หน้า 2, 4

#### Trade-off / Benchmark / Threats to Validity

**คำอ่าน:** เทรด-ออฟ · เบนช์มาร์ก · เธรตส์ ทู วะลิดิที

**ความหมาย:** Trade-off คือได้ประโยชน์ด้านหนึ่งโดยมีต้นทุนอีกด้าน Benchmark คือการทดสอบเทียบภายใต้เงื่อนไขกำหนด Threats to validity คือปัจจัยที่จำกัดความน่าเชื่อถือหรือการขยายข้อสรุป

**ที่มาของแนวคิด:** ผลวัดตอบคำถามภายในขอบเขตทดลอง การวิจารณ์ต้องแยกระหว่างผลไม่ดีจริงกับข้อมูลที่ยังไม่เพียงพอ

**เหตุที่เกี่ยวข้อง:** พื้นที่และ hydration เป็นต้นทุนที่มีหลักฐาน ส่วนมือถือ WAN และข้อมูลสดยังไม่ถูกทดสอบใน PDF

**ตัวอย่างใช้งาน:** ผลบน local server ใช้ตั้งสมมติฐานสำหรับทดสอบบนมือถือได้ แต่ไม่แทนผลมือถือโดยตรง

**คำเกี่ยวข้อง:** SC — Storage Cost / Deployment Footprint · Network Transfer / Local Server / WAN · Data Freshness / Cache Invalidation

**อ้างอิงบริบท:** §3–5 · PDF หน้า 2–4; กรอบวิจารณ์เป็นการวิเคราะห์ระบบ

### คำถามตรวจความเข้าใจ

**Hydration ละเอียดขึ้นมีผลวัดใหม่ในบทความหรือไม่?**

ไม่มี §5 เสนอให้ศึกษาต่อจากคอขวดที่วัดได้

**Hybrid กับ Incremental ต่างกันอย่างไร?**

Hybrid ผสานช่วงเผยแพร่กับรันไทม์ ส่วน Incremental สร้างผลใหม่เฉพาะส่วนที่เปลี่ยน ทั้งสองใช้ร่วมกันได้แต่ไม่ใช่คำเดียวกัน

**Automatic configuration หมายถึงใช้ AI หรือไม่?**

ไม่ เอกสารเสนอเป้าหมายการเลือกตามข้อมูลกับข้อกำหนด แต่ไม่ได้กำหนดว่าใช้ AI
